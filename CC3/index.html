CC3

在前面分析的链子中，都是利用反射触发Runtime.getRuntime().exec()去执行命令的，那么如果代码中的黑名单禁用了Runtime，那么就可以通过 CC3这条链来解决。

CC3不借助Runtime类中的exec去执行命令，而是利用类加载机制，动态加载恶意类来实现自动执行恶意类代码

根据Java类的动态加载原理，我们知道动态类加载可以通过ClassLoader来完成。而其中有个ClassLoader.defineClass可以从字节码加载任意类，这也是 CC3的sink点。

Java文件的编译

Java文件编译过程主要包括两个阶段，第一阶段是在编译阶段将源码文件.java编译成对应的字节码文件.class 的过程，在书中这种编译器常常被叫做前端编译器，第二阶段（可选）为在运行的时候，通过 JVM的编译优化组件，对代码中的部分代码编译成本地代码，也就是 JIT编译，例如 HotSpot中的C1、C2编译器

.java源代码 → 词法分析 → 语法分析 → 语义分析 → 注解处理 → 字节码生成 → .class文件

类加载过程

类想要运行使用，必须先载入 JVM（虚拟机）；JVM 会先去方法区查找该类的Class信息，如果已经存在就直接复用，不存在则由类加载器执行加载。

然后当程序主动使用某个类的时候，如果该类还未被加载到内存中，系统会通过：加载 → 连接（验证、准备、解析）→ 初始化。三个步骤来对该类进行初始化。

  • 静态成员存入静态区，在类初始化阶段处理；非静态成员属于对象，要等到实例创建时才分配；
  • 静态代码块：类初始化的时候自动执行；非静态代码块、构造器：只有 new 创建实例才执行；
  • 执行顺序：先父类、后子类；先静态、后非静态；
  • 静态方法、普通成员方法都属于被动调用，不调用就不会执行。

类加载器执行流程：类加载器 → 查找字节码 → 读取字节流 → 方法区存储 → 创建 Class对象

主要是这三件事：

  • 通过全限定名获取定义此类的二进制字节流。
  • 将字节流所代表的静态存储结构转换为方法区的运行时数据结构。
  • 在堆中生成java.lang.Class对象

加载主要还是靠我们的类加载器去完成的，类加载器有多种，当我们想要加载一个类的时候，具体是哪个类加载器加载由 双亲委派模型 决定。并且每个Java类都会有一个引用指向加载它的ClassLoader

Java类加载器

类加载器（class loader）用来加载 Java 类到 Java 虚拟机中。

官方总结：Java类加载器（英语：Java Classloader）是Java运行时环境（Java Runtime Environment）的一部分，负责动态加载Java类到Java虚拟机的内存空间中。类通常是按需加载，即第一次使用该类时才加载。由于有了类加载器，Java运行时系统不需要知道文件与文件系统。

JVM 中有3个默认的类加载器：
1、启动类加载器 （Bootstrap Class Loader）
2、扩展类加载器（Extension Class Loader）
3、应用程序类加载器（Application Class Loader）

为什么要有三个类加载器，一方面是分工，各自负责各自的区块，就如Application Class Loader主要负责加载用户之间开发的代码，另一方面为了实现委托模型。

一个应用程序总是由n多个类组成，Java程序启动时，并不是一次把所有的类全部加载后再运行，它总是先把保证程序运行的基础类一次性加载到jvm中，其它类等到jvm用到的时候再加载。

双亲委派

双亲委派机制是从安全角度出发的，根据 Java 的类加载器的多层，可参考以下图片：

双亲委派模型，要求除了顶层的启动类加载器外，其余的类加载器都应当有自己的父类加载器。

  • ClassLoader、SecureClassLoader、URLClassLoader、AppClassLoader、ExtClassLoader：全都是 Java 源码，可以在 OpenJDK 里直接翻、断点调试
  • BootstrapClassLoader（启动 / 引导类加载器）：不是 Java，HotSpot 里面是 C++ 写的，属于 JVM 本身，拿不到 Java 对象，代码里用 null 代表它

Java平台通过委派模型去加载类。每个类加载器都有一个父加载器。
1、当需要加载类时，会优先委派当前所在的类的加载器的父加载器去加载这个类。
2、如果父加载器无法加载到这个类时，再尝试在当前所在的类的加载器中加载这个类。

或者这张图片：

机制好处：
1、因为双亲委派是向上委托加载的，所以它可以确保类只被加载一次，避免重复加载
2、避免核心类被串改：Java的核心API都是通过引导类加载器进行加载的，如果别人通过定义同样路径的类比如java.lang.Integer，类加载器通过向上委托，两个Integer，那么最终被加载的应该是jdk的Integer类，而并非我们自定义的，这样就避免了我们恶意篡改核心包的风险

其实自己测试的话应该会报错。

动态加载字节码（.class）

严格来说，Java 字节码（ByteCode）其实仅仅指的是 Java 虚拟机执行使用的一类指令，通常被存储在 .class文件中。而字节码的诞生是为了让 JVM 的流通性更强，如图

反序列化链里用来加载字节码的类加载器，本质就是拿到一个 ClassLoader 对象，调用它的 loadClass；加载逻辑是类加载器自带源码实现，我们只负责驱动这个方法跑起来。

类加载器的原理

在loadClass()方法被调用的时候，是不进行类的初始化的。

双亲委派机制类加载访问流程：

  • 继承链： ClassLoader → SecureClassLoader → URLClassLoader → AppClassLoader（JDK8）
  • 加载调度： loadClass()（调度入口） → 双亲委派向上走 → findClass()（真正读字节码）

分析一下每个步骤：

  • ClassLoader：抽象根类，承载 loadClass，双亲委派核心调度
  • SecureClassLoader：安全层，校验代码源与签名
  • URLClassLoader：从 URL / Jar 读取 class 字节，重写 findClass
  • AppClassLoader：URLClassLoader 的实例，加载 classpath 下的业务与依赖包
  • loadClass：委派入口，先缓存 → 向上交给父加载器 → 失败才调用 findClass
  • findClass：实际读取字节码、生成 Class 的方法，由子类实现

CC3 就是利用Transformers链条最终走到loadClass，加载恶意类；所以必须搞懂什么时候会触发loadClass、findClass、双亲委派什么时候放行。

关键记忆（对CC3）：

  • parent 是构造传入的委派对象，和 extends 没有任何强制绑定；
  • CC 整套链基本跑在 JDK8，所以 JDK8：AppClassLoader是URLClassLoader的子类；
  • loadClass / findClass 是方法，不是类，不能放进类继承链条。

PS:

JDK 9+（模块化，变化巨大）:

JDK9 之后直接砍掉：AppClassLoader / PlatformClassLoader 不再继承 URLClassLoader，改成内部 BuiltinClassLoader：

此时 AppClassLoader 和 URLClassLoader 已经没有继承关系了，URLClassLoader 退化成一个普通工具加载器OpenJDK。

小结

类加载的 初始化阶段（clinit），会自动执行静态代码块、静态变量赋值逻辑，这就是 CC3 的核心根基；普通方法、非静态代码块不会在这里执行。

我们找一个能被反序列化链调到 loadClass 的入口，加载一个恶意类；一旦成功加载并走到初始化，里面静态块的恶意代码就自动执行，不需要再手动调用方法。

不是只要 loadClass 就一定会触发静态块；默认 loadClass 很多时候只加载、不初始化，这也是 CC3 需要特定调用链路去推动走到初始化的原因。

URLClassLoader类加载class文件

URLClassLoader 实际上是我们平时默认使用的 AppClassLoader 的父类，所以，我们解释 URLClassLoader 的工作过程实际上就是在解释默认的 Java 类加载器的工作流程。

正常情况下，Java会根据配置项 sun.boot.class.path 和 java.class.path 中列举到的基础路径（这些路径是经过处理后的 java.net.URL 类）来寻找.class文件来加载，而这个基础路径有分为三种情况：

1、URL未以斜杠 / 结尾，则认为是一个JAR文件，使用 JarLoader 来寻找类，即为在Jar包中寻找.class文件
2、URL以斜杠 / 结尾，且协议名是 file ，则使用 FileLoader 来寻找类，即为在本地文件系统中寻找.class文件
3、URL以斜杠 / 结尾，且协议名不是 file ，则使用最基础的 Loader 来寻找类。
