简介

Commons Collections

根据维基百科，Apache Commons 是 Apache 软件基金会的项目，曾隶属于Jakarta 项目。Commons 的目的是提供可重用的、开源的 Java 代码。Commons 由三部分组成：Proper（是一些已发布的项目）、Sandbox（是一些正在开发的项目）和 Dormant（是一些刚启动或者已经停止维护的项目）。

Apache Commons 当中有⼀个组件叫做 Apache Commons Collections ，主要封装了Java 的 Collection(集合) 相关类对象，它提供了很多强有⼒的数据结构类型并且实现了各种集合工具类。

Commons Collections 包为 Java 标准的 Collections API 提供了相当好的补充。在此基础上对其常用的数据结构操作进行了很好的封装、抽象和补充。让我们在开发应用程序的过程中，既保证了性能，同时也能大大简化代码。

相关利用链

CC 链便是 Apache commons collections 反序列漏洞利用链的简称。 Apache Commons Collections 中有⼀个特殊的接口，其中有⼀个实现该接口的类可以通过调用 Java 的反射机制来调用任意函数，叫做 InvokerTransformer …

手写 Poc 复现 CC

根据我看了这么久认为，理解一个东西不能太片面，我们做什么事要有目的有原因，有始有终。先参考一下CC1链结构：

Runtime.exec()

所以先不管此链入口类什么的，我们先说什么造成了最终的 RCE，就是Runtime这个类，其中的危险方法：Runtime.exec()。

查看源码可知，exec()是实例方法，必须依托实例对象调用，不能直接通过类名调用；Runtime的构造方法私有，是单例模式，无法通过 new 创建对象，只能调用它提供的静态方法getRuntime ()获取唯一实例，再调用exec执行命令。

先看看那个静态方法（PS：静态成员变量不能被序列化：序列化是针对对象属性的，而静态成员变量是属于类的。）：

可知getRuntime()就是用于获取当前的Runtime()对象，且getRuntime() 是static 静态方法，可直接通过类名调用。

即获取实例对象：Runtime.getRuntime()，它可返回 Runtime 的唯一实例对象，获取了之后即可调用里面的exec方法，原生用法：

值得注意的是，在后面构造 CC1 链的时候不能直接Runtime.getRuntime()来获取实例对象，一是Runtime实例不可序列化，二是序列化存储的是本地对象状态，不能存储代码执行逻辑。下面这样的话写只是为了测试

第二点也就是说序列化只能存对象和它里面成员变量的值，不能存一段保存代码执行逻辑。
Runtime.getRuntime().exec("calc") 是一行执行逻辑，不是一个可以打包序列化带走的对象。
我们想要的效果，是在受害机器上执行这一套调用，而不是在本地生成 payload 的时候就执行。

所以我们需要通过反射的方法去调用getRuntime()，在目标端远程 “唤起” ，从而实现 RCE。

entrySet() 用法

entrySet()这个方法里面的map就是我们下面构造的 Payload 传递进去的被decorate修饰后的map，过一下isSetValueChecking() 判断一下值是否为空，就会实例化一个EntrySet静态方法对象，再entrySet()[ 下面会介绍作用 ]一下把 map 里面所有的键值对（key-value）打包成一组 Entry 对象（ this 就是指向方法调用者，在下面的for循环里为：tMap），然后根据这三个静态类层层传递就会到MapEntry类这里，不过传递的时候通过parent来进行。

parent 是被 decorate 修饰后的整个 TransformedMap 对象（tMap），entry 才是单条键值对。

MapEntry 在实例化时接收两个入参：底层原生的键值对 Entry，以及一路传递下来的 parent（TransformedMap），后续 setValue 时通过这个 parent 调用 checkSetValue 触发转换器。

再解释一下 Poc

其实根据我们之前介绍AbstractInputCheckedMapDecorator里的entrySet() 类以及三个静态方法就可以清楚地知道此 Payload 运行流程了，这里再简述一下：

1、首先要知道tMap.entrySet() 这里：我们知道TransformedMap的父类为AbstractInputCheckedMapDecorator，该代码实现的时候，先在子类TransformedMap里找entrySet()，没有，所以根据多态的思想会去父类AbstractInputCheckedMapDecorator类里面成功找到entrySet()。

2、然后我们知道tMap对象是被decorate修饰过的，tMap 里面有一个valueTransformer成员变量，这个 valueTransformer 才是我们 Payload 传入的 invokerTransformer，所以它就相当于invokerTransformer。

tMap 以 parent 的身份进入entrySet() 后，根据前面所述，它会一路向下传递给MapEntry这个类；迭代遍历的时候，取出底层原生 Entry，构造 MapEntry(原生entry, parent=tMap)。然后实现parent.checkSetValue(value);。

3、然后我们前面知道TransformedMap 重写了 checkSetValue 方法，内部执行 valueTransformer.transform(value)，也就是 invokerTransformer.transform(value)。 所以最后 entry.setValue() 触发钩子时，链路走到 parent.checkSetValue()，最终执行 invokerTransformer.transform()，反射调用目标方法，完成 RCE。

4、我们这里的目标设置的值就是 Runtime 的对象

AnnotationInvocationHandler

右键查找用法，在1.8/sun.reflect.annotation里面的AnnotationInvocationHandler.java下就有一个方法实现了setValue方法，并且十分巧的是这个方法也是readObject实现了setValue方法。

因为我们最后序列化完了，序列化后的对象是 AnnotationInvocationHandler 实例，所以反序列化的时候，会执行 AnnotationInvocationHandler.readObject()！！从而完成链的实现

更巧的是，AnnotationInvocationHandler类是可序列化的。那这里明显就是最终出口了。

AnnotationInvocationHandler 本身就是 JDK 专门用来【注解代理】的 InvocationHandler，它的构造器强制要求传入一个合法注解 Class，源码构造器里做了强校验，不满足注解直接抛异常，所以后面必须传注解。

ConstantTransformer

这个简单先分析这个，主要源码如下：

super()：调用父类的无参构造。

  • super() 只是走一遍父类初始化，没有任何业务逻辑，不存值、不改变行为
  • Java 里如果你不写super()，编译器也会自动帮你加上。删掉这一行，功能一模一样。

transform(Object input) 这是 CC1 用到的核心方法：无视传入的 input（也就是那个不可控的 AnnotationTypeMismatchExceptionProxy），直接返回预先存好的 iConstant。

它在正常业务中，它本来就是用来 “强制输出固定值，无视输入” 的通用转换工具，所以在这里，构造时保存常量对象到iConstant，transform方法忽略输入input，直接返回iConstant，以此解决setValue传入参数不可控的问题。

Q：为啥一步步获取不用原生Runtime.class反射，要用一堆InvokerTransformer？

  • 原生反射写在代码里，序列化阶段就执行，会生成不可序列化的 Runtime 实例，序列化直接报错；
  • 原生反射是一段执行代码，无法序列化传输给目标机器；
  • InvokerTransformer把反射逻辑包装成可序列化的对象（只存方法名字符串），反射动作延迟到反序列化触发时执行；
  • 因为反射是分步链式依赖，一步做不完，所以需要多个Invoker接力。

或者写：

把这上面完整原生反射代码，拆成三步方法调用，包装成三个InvokerTransformer，再在前面加上一个可被序列化的Runtime.class对象，串联在Chained里。

3 个InvokerTransformer都是在被重写的有反射调用逻辑的transformer方法里实现的。

详细解释一下：

第 1 个：new ConstantTransformer (Runtime.class)

  • 输入：AnnotationTypeMismatchExceptionProxy（上游传进来的，我们不想要）
  • 作用：无视输入，直接固定返回 Runtime.class
  • 输出：Runtime.class（Class 对象，实现了 Serializable，可以序列化，不会报错）

第 2 个：InvokerTransformer ("getMethod", new Class []{String.class, Class [].class}, new Object []{"getRuntime", new Class [0]})

  • 输入：上一步输出的 Runtime.class
  • 含义：调用输入对象的 getMethod 方法
  • 等价原生代码：Runtime.class.getMethod("getRuntime", new Class[0])
  • 作用：获取 getRuntime() 这个静态方法对应的 Method 反射对象
  • 输出：Method 对象（getRuntime 方法）

第 3 个：InvokerTransformer ("invoke", new Class []{Object.class, Object [].class}, new Object []{null, new Object [0]})

  • 输入：上一步输出的 Method 对象
  • 含义：调用 Method 对象的 invoke 方法
  • 等价原生代码：method.invoke(null, new Object[0])
  • 重点：getRuntime 是静态方法，invoke 第一个参数传null；该方法无参数，传空数组
  • 输出：Runtime 实例对象

第 4 个：InvokerTransformer ("exec", new Class []{String.class}, new Object []{"calc"})

  • 输入：上一步输出的 Runtime 实例
  • 含义：调用 Runtime 实例的 exec 方法
  • 等价原生代码：runtime实例.exec("calc")
  • 作用：执行系统命令，弹出计算器
  • 输出：进程对象

一些利用入口

不仅是可控反序列化接口可作为入口，很多时候不是 HTTP 直接传序列化数据，还有一些衍生场景：JRMP、RMI等，以及一些小众入口

例如RMI 服务：

  • RMI 底层通信协议本身就是 Java 序列化；
  • 服务端开放 RMI 端口，接收 RMI 请求，自动对传入参数反序列化；
  • 攻击者向 RMI 端口发送 CC1 序列化 payload；
  • RMI 服务内部自动 readObject，触发链子执行命令。

小众入口：

  • 存储类：从 Redis/Mysql 读取序列化对象：
    • 老系统把对象序列化后存 Redis，key/value 由外部可控；攻击者可以覆盖 Redis 里的 value 为恶意序列化 payload，后端读取后反序列化触发。
  • 文件上传：上传序列化文件，服务端读取解析：
    • 上传.ser序列化文件，后端读取文件并反序列化。
  • Shiro 反序列化
    • Shiro 是 CC1 最出名的落地场景，Shiro RememberMe 功能：
      • 用户勾选记住我，Shiro 会把用户信息序列化，AES 加密后放到 Cookie rememberMe；
      • 如果密钥泄露（默认密钥或者可猜测密钥）；
      • 攻击者可以自己构造 CC1 payload，用这个密钥加密，放到 Cookie 里发给后端；
      • 后端拿到 Cookie → AES 解密 → 得到序列化字节 → readObject() 反序列化 → 触发 CC1 RCE。
    • 这就是 Shiro-550，底层就是 CC1 链，不过 Shiro 不是直接传序列化字节，是加密包装后的序列化 payload，CC1 是里面的执行链。
