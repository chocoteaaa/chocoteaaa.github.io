工具简介

基础信息

sqlmap 是 Python 编写、开源 GPLv2 协议 的 SQL 注入自动化检测 + 利用工具，作者：Bernardo Damele、Miroslav Stampar，2006 年发布，官网：sqlmap.org，GitHub也有。

Kali、Parrot 等渗透系统预装；Windows / MacOS 只要有 Python3 都可以手动部署。 核心定位：把手工 SQL 注入的整套流程自动化，是网安行业 SQL 注入测试的标准工具。

核心能力总览

  • 自动检测：识别注入点、自动判断注入类型、指纹识别后端数据库
  • 信息枚举：库、表、字段、数据、账号密码哈希、权限、版本、操作系统
  • 高级利用（依赖 DBA 权限 + 数据库配置）：读取文件、写入文件、执行系统命令、获取交互式 OS Shell、OOB 带外数据外带
  • 辅助能力：绕过 WAF（tamper 脚本）、代理、Cookie/Header 注入、会话保存、密码哈希自动字典爆破

支持 40+ 数据库：MySQL、MSSQL、Oracle、PostgreSQL、SQLite、Access、DB2、ClickHouse、TiDB、Redshift 等传统和云数据库sqlmap。

sqlmap 不是万能：存在误报（假阳性），工具提示注入成功，必须手工构造 payload 复核；WAF、复杂过滤场景很容易检测失败。

六大注入原理

标记 注入类型 原理简述 适用场景
U Union 联合注入 拼接 UNION SELECT，直接把数据输出到页面 页面有回显，速度最快，优先使用
E 报错注入 利用数据库报错函数（updatexml/extractvalue 等），错误信息带出数据 网站开启数据库报错
B 布尔盲注 构造真假条件，对比页面内容 / 长度差异判断结果 无报错、无数据回显，但页面内容有变化
T 时间盲注 注入延时函数 sleep ()、benchmark ()，根据响应延迟判断真假 页面完全无任何差异，最慢
S 堆叠注入 分号 ; 执行多条独立 SQL 语句 MSSQL 最友好；MySQL 受驱动限制经常不支持
Q OOB 带外注入 数据库主动发起 DNS/HTTP 请求，把数据带出（DNSlog） 页面无回显、盲注速度太慢时神器

默认检测顺序 BEUSTQ，全部类型尝试；我们可以手动指定只启用某几种提速。

本质：和手工注入逻辑一模一样，只是 sqlmap 内置海量 payload、二分查找算法自动猜字符，代替人反复发包比对响应。

优缺点

优点

  • 标准化成熟，覆盖绝大多数注入场景
  • 内置二分算法，盲注效率远高于手工
  • 屏蔽各数据库语法差异
  • 自动结构化导出数据，方便写报告
  • 支持代理、延时、随机 UA、会话缓存、OOB 等辅助能力

缺点

  • Payload 特征明显，极易被 WAF 识别拦截
  • 复杂自定义过滤、特殊编码场景灵活性弱于手工注入
  • 盲注发包量大，容易触发风控封 IP
  • 只能处理注入类漏洞，无法检测 XSS、文件上传等漏洞

七段标准实操流程

最简主线命令，靶场 80% 场景够用：

装载目标：选择输入源

推荐先 -r req.txt，Burp 抓包直接保存，Cookie、请求头、JSON 全部自动带上，不用手动填一堆参数。

方式 命令 适用场景 新手提示
请求文件（首选） sqlmap -r req.txt Burp 导出原始包 JSON、Cookie 复杂请求首选
URL GET sqlmap -u "http://xxx?id=1" 简单 GET 参数 最简单，但缺少上下文
Burp 日志批量 sqlmap -l burp.log --scope='regex' 批量筛选目标 后期批量测试用
自动解析表单 sqlmap -u <url> --forms 自动抓取页面 form 表单 不会抓包的时候用
爬虫发现入口 sqlmap -u <url> --crawl=2 自动爬页面找参数 适合入门小站点
挖掘隐藏参数 sqlmap -u <url> --mine-params? 探测页面未显式携带的 GET 参数 进阶（非 sqlmap 原生）
OpenAPI 导入 --openapi=api.json 从 Swagger 接口文档生成目标 进阶（xray 等工具的能力）

--mine-params、--openapi 是 xray 的参数，不是 sqlmap 的参数；

sqlmap 里想 “挖隐藏参数” 通常靠 --crawl（爬行）+ --forms（表单）+ Burp 抓包补参，或直接用 Arjun 跑参名字典。上表前 5 行才是纯 sqlmap 的常用入口。

定点筛选参数：

  • -p "id,name"：仅测试指定参数
  • --skip=csrf：跳过指定参数
  • --param-exclude='^(utm_|_t$)'：正则排除参数
  • --param-filter='GET'：按请求位置筛选参数

-u 默认只处理 GET；JSON 请求优先 -r；--data传 JSON POST 要手动加 --headers="Content-Type: application/json"；--data默认 POST，其他请求方法搭配 --method。

请求对齐：发包和浏览器保持一致（排错高发段）

新手排错手段：-v 3，查看 sqlmap 真实发送数据包，对比 Burp 里浏览器的包，很多时候不是没有注入，是发包缺 Cookie、头不对。

探测与判定：先轻后重 + 判空校准

默认配置：--level=1 --risk=1 --technique=BEUSTQ，不要上来直接拉满 level=5 risk=3。

参数 作用 新手使用建议
--level 1~5 探测广度：1 默认 (GET/POST)；2 增加 Cookie；3 增加 UA/Referer；4-5 大量 Payload 变体 靶场一般 1~3 足够
--risk 1~3 风险等级：1 只读安全；2 加重延时盲注；3 包含 OR 类 Payload，可能修改数据 永远不要随便用 3
--technique 限定注入类型，降噪提速 有回显优先 --technique=U；无回显用 --technique=T
--smart 启发式过滤，只对疑似注入点深度测试 批量扫描降噪
--time-sec 盲注延时时间，默认 5s 网络卡的时候调到 7~10
--proof（1.10 新） 输出可用于报告的注入证明 Payload 写漏洞报告用
--tamper Payload 变形绕过简单 WAF，内置 84 个脚本 靶场一般不用，被 WAF 拦截再试

判空校准（页面内容一直在变、动态页面，容易误判，这一组参数用来校准判断依据）： --string / --not-string / --regexp / --code=200 / --text-only / --titles / --lengths

假阴性排查顺序： --flush-session → 调高--level → 更换--technique → 搭配--tamper；还是不行，就是目标有拦截，不要无限反复跑。

WAF 识别已经内置自动化，--identify-waf 废弃，不需要手动调用。

指纹与权限画像：判断你能拿到多少权限

判断链路：
DBA + 文件读写权限 → --file-read/--file-write
DBA + 堆叠 S 支持 → --os-shell
普通账号只有 SELECT 权限 → 只能老老实实枚举库表数据

枚举：精准优先，拒绝全量爆破

避雷：真实测试环境不要用 -a、--dump-all，流量巨大，日志爆炸。

缓存坑：sqlmap 会缓存探测结果；改了 tamper、参数之后旧结果不会自动刷新。

  • --fresh-queries：重新查询数据
  • --flush-session：清空全部会话记录，重新探测

高阶利用（必须 DBA 权限，门槛高，先了解，不要一上来就冲 shell）

重点提醒：MySQL 环境 os-shell 成功率很低，受 secure_file_priv、网站物理路径、目录写入权限三重限制；MSSQL 堆叠更容易拿到命令执行权限。建议先在靶场尝试 --sql-shell，更容易成功。

持久化与会话：sqlmap 是有状态工具

默认会话、日志、导出数据存放路径：~/.sqlmap/output//

参数 作用 新手理解
-s file 自定义会话文件 保存探测记录，下次接着跑
--output-dir=DIR 自定义输出根目录 改导出文件位置
-t traffic.log / --har=x.har 保存完整 HTTP 流量 取证、复盘发包
--dump-file=x.csv / --report-json=x.json（1.10） 自定义导出、JSON 报告 导出结构化报告
--save=cfg.ini → -c cfg.ini 保存配置文件 一长串命令存成配置，一键复用
--batch / --answers / -z "flu,bat" 无人值守自动应答 写脚本批量跑的时候用
-m bulk.txt 批量多目标扫描 批量 url
sqlmapapi.py -s 启动 REST 接口 代码调用 sqlmap，进阶

最高频排错参数：--flush-session，怀疑结果不对、缓存污染，优先加上。

CTFShow练习

web201

提示：

  • 使用--user-agent 指定agent
  • 使用--referer 绕过referer检查
  • 后端：select id,username,password from ctfshow_user where username !='flag' and id = '$_GET[id]';

分析

关键前置条件（注入点）：页面表单实际请求的是 GET /api/?id=（不是 /sqlmap.php?id=），在前端js里就可以读出来，可以直接硬看js，但推荐用以下步骤：

  1. 浏览器打开页面，F12 → Network → 勾 Preserve log
  2. 写个数字，点一次“查询”按钮
  3. 找到那条 XHR（本题是 api/?id=1），右键 → Copy → Copy as cURL
  4. 存成 req.txt，注意两点：
    • 本题要把 User-Agent 改成含 sqlmap 的（浏览器 UA 会被 WAF 拒）
    • Referer 保留 https://ctf.show/
  5. 直接喂给 sqlmap： sqlmap -r req.txt --batch --dbs

为什么优先 -r 而不是 -u：-r 把 Cookie、Referer、Content-Type、JSON body、自定义 Header
全部原样带上，而入口发现阶段最容易出错的就是“少带了一个头”。

本题就是例子：-u 能跑通，但前提是你手工补齐了 Referer；换一道依赖 Cookie/CSRF token 的题，-r 几乎不用补任何东西。

  1. 总结：入口发现推荐顺序，成本从低到高

看 HTML 源码（grep action/input）
→ 看 JS（grep url/fetch/ajax）
→ F12 Network 点交互
→ 抓包工具记录
→ 爬虫批量扫

分析

执行链

    • --current-user = root@localhost，--is-dba = True

测试

先确认 DBA：

方法1：交互式 os-shell（管道喂命令）

方法2：非交互式执行命令

--web-root=/var/www/html可以不加，去掉 --web-root 后，sqlmap 在 --batch 模式下会：

  • 提示选择后端语言，默认 PHP
    • 自动遍历默认 web 根目录列表
    • 在 /var/www/html 找到可写目录，上传 stager + backdoor

两个方法区别

两个方法都是 getshell，而且底层是同一套东西：sqlmap 往 /var/www/html 写一个临时 PHP 后门（web backdoor），通过它执行系统命令，退出时再删掉。

区别只在交互方式：

–os-cmd=”id” –os-shell
输入 一次一条命令，执行完退出 交互式，可连续输多条
生命周期 跑完即清理 保持到 exit/q 再清理
上传物 stager + PHP backdoor 同样
权限 继承 web 进程（本例 www-data） 同左

所以准确说法是：

  • 二者都是 webshell 形式的临时 RCE，不是持久化 webshell，也不是反弹 shell
  • --os-cmd = 一次性命令执行（自动化友好）
  • --os-shell = 同一个后门上的交互式系统 shell

如果要持久 webshell（后门不删）或反弹 shell，那 sqlmap 的这两个参数都不直接给：

  • 持久化：用 --os-shell 里的命令自己写一个马，或 --file-write 上传
  • 反弹 shell：用 --os-pwn（走 SQL 注入的 OOB，需 Metasploit，属于另一条链），或在 shell 里自己执行 bash -i >& /dev/tcp/...

另外提醒：这题 sqlmap 退出后确实把 tmp*.php 清理干净了（我复核过 /var/www/html），所以严格说它确实就是「临时getshell」，不是「留后门」。

结果

  • --os-shell 三个前提（本题PHP+MySQLroot全满足）：
    • 堆叠查询可用
    • DB用户DBA/FILE权限
    • web目录可写
  • 首次运行会遍历默认 web 根目录，/var/www/ 失败是正常的，/var/www/html 才成功
  • 非交互环境必须 --batch + 管道输入 + --web-root，否则会卡在菜单
  • 退出时 sqlmap 会删掉上传的 php；仍建议手工 ls 确认一次
  • --os-cmd 适合一次性验证，--os-shell 适合连续操作，底层链路相同
