XXE基础

发表于2026-10-12|更新于2026-10-12
|总字数:5776|阅读时长:24 分钟|浏览量:

以前打 CTF 的时候，这个题没学过，不会做，学长手把手教了，一直没机会复习，今日一看，也不过如此嘛

XXE（XML External Entity，XML外部实体注入） 是一种针对XML解析器的安全漏洞。当应用程序使用配置不当的XML解析器处理用户可控的XML输入时，攻击者可以通过构造恶意的外部实体声明，诱导服务器读取本地文件、发起内部网络请求、执行拒绝服务攻击，甚至在某些条件下实现远程代码执行。

该漏洞被OWASP列为2017年十大应用安全风险之一

XML

XML：可扩展标记语言（Extensible Markup Language）
核心定位：一种通用的文本格式，把复杂数据，用自定义标签组织起来，用来存储、传输结构化数据。

重点：XML 不是编程语言，只是数据格式，和 JSON 是同类东西，JSON 是它的简化替代品，早期 Web 接口大量用 XML，现在更多用 JSON 替代。

为什么早年接口爱用 XML 而现在多用 JSON？
答：XML 支持 DTD、实体、命名空间等丰富特性，这些额外特性（实体）正是 XXE 漏洞来源；JSON 没有 DTD 和实体，天然不会产生 XXE。

XML 示例：

核心特点

可自定义标签，不像 HTML 标签固定。HTML 是用来展示页面；XML 是用来描述数据。

标签student、name都是我们自己定义的。
结构树形、有开始闭合标签，支持嵌套。
自带 DTD/XSD，能做数据格式校验（这部分实体机制，就是 XXE 漏洞的来源）

XML 主要用途

前后端 / 系统之间传输数据

早年 WebService、SOAP 接口，就是用 XML 传数据，现在大多换成 JSON。

这就是XXE 最常出现的场景：后端接收客户端提交的 XML，调用解析器解析。

程序配置文件

用来存软件、框架的配置信息：

  • Java Maven：pom.xml（项目依赖配置）
  • Spring：applicationContext.xml、beans.xml（spring bean 配置）
  • Android 旧版布局文件 layout.xml
  • 各类软件、游戏配置文件

这类配置 XML：开发写死，普通用户不能随便提交修改，所以一般不会触发 XXE。

文件底层存储格式

很多文件本质是压缩包，里面包含一堆 XML：

  • Office：docx、xlsx（解压后里面全是 xml）
  • SVG 矢量图：.svg 本身就是纯 XML 文件（svg 上传是经典 XXE 攻击点）
  • OpenOffice 文档

数据持久化存储

小型系统把数据直接保存在 xml 文件里代替数据库（现在很少用）

XML vs JSON

  • XML：标签成对，体积大，支持 DTD 实体（有 XXE 风险），支持注释
  • JSON：更轻量，简洁，没有实体机制，天然不存在 XXE 漏洞

所以现在新项目优先 JSON，规避 XXE。

与 Java 的 pom.xml

pom.xml 是 Maven 项目的项目配置文件，是存放在 Java 项目源码里的本地配置文件。

  • 作用：Maven 用它管理项目依赖、版本、打包、插件；
  • 位置：项目根目录，是开发人员写好、放在服务器 / 源码仓库的静态文件；
  • 本质：静态配置文件，不是用来接收用户输入的。

XML 工作原理

（正常业务工作原理）业务系统之间，用 XML 文本承载结构化数据；程序调用 XML 解析器，把文本字符串 → 内存对象，供代码读取使用。

完整业务流程

生命周期：原始XML文本（网络传输/磁盘文件）→XML解析器→内存树形数据→业务代码读取数据执行业务
例子：客户系统调用我们的 WebService 接口，上传订单信息（接收 XML 接口场景，最容易出现 XXE 的场景，）
数据封装（发送方） 发送方（客户端）按照约定格式，把订单数据写成 XML 文本：

通过 HTTP POST 请求发给后端，Content-Type: application/xml。
后端接收原始 XML 字符串 Java Web 后端（Spring 等）从请求 Body 拿到一大段字符串，此时它还只是文本，程序看不懂里面的标签含义。
调用 XML 解析器解析 后端代码调用解析器（SAX / DOM / DOM4j）读取这段 XML 字符串：

  • 解析器逐行扫描标签，识别开始标签、结束标签、嵌套关系
  • 构建树形结构（DOM 树）放到内存
  • 业务代码就可以读取节点：获取 orderId、price 等字段，执行业务逻辑（入库、生成订单）

正常情况：XML 只有普通标签，没有、实体定义，不会读取外部文件。
攻击情况：攻击者把请求里的 XML 替换成带外部实体的恶意 XML，如果解析器没关闭外部实体，解析器就会去读取file://本地文件，触发 XXE。

读本地 XML 配置文件（pom.xml/spring beans.xml）

1、程序启动时，去磁盘读取本地 xml 文件（开发预先写好，用户不可控）
2、XML 解析器读取磁盘上的文件文本
3、解析成内存数据，加载配置（Maven 读取 pom、Spring 加载 Bean）
4、解析完成，把配置信息交给程序使用

重点： 这份 xml 在磁盘上，普通 Web 用户无法修改。 就算解析器开了外部实体，攻击者不能修改 xml 内容，无法注入恶意实体，不会产生 XXE。

XML 解析两种模式（DOM 和 SAX）

DOM（文档对象模型）

  • 一次性把整个 XML 全部读入内存，构建完整树形对象
  • 优点：可以随机增删改节点
  • 缺点：XML 很大时占用内存高；DOM 解析器常出现 XXE

SAX（简单 API for XML）

  • 事件驱动，一行一行流式读取，不一次性加载完整树到内存
  • 读到开始标签、文本、结束标签触发回调函数
  • 优点：省内存，适合大 XML
  • 注意：SAX 如果没关闭外部实体，同样存在 XXE 漏洞！

两者只是读取方式不同，只要开启 DTD / 外部实体，就都有 XXE 风险

DTD 在正常业务的作用

这就是 XXE 漏洞的源头特性，DTD（文档类型定义）：用来约束 XML 的格式，校验 XML 结构是否合法。
正常业务场景：预先定义 DTD，规定 XML 里面必须有哪些标签、标签类型。

有了 DTD 的具体作用：

  • 每一个 XML 文件均可携带一个有关其自身格式的描述。
  • 独立的团体可一致地使用某个标准的 DTD 来交换数据。
  • 应用程序也可使用某个标准的 DTD 来验证从外部接收到的数据。
  • 还可以使用 DTD 来验证您自身的数据。

解析器解析 XML 时，会对照 DTD 检查：标签有没有少、结构对不对。

若规范里 DTD 支持 <!ENTITY> 实体，实体可以引用外部资源，这个可选扩展特性，被攻击者利用就是 XXE。

<!ENTITY>

作用：定义实体（变量）

  • SYSTEM 关键字：代表外部实体，可以引用外部资源（本地文件、http 地址）
  • 使用方式：&flag; XXE 核心，用来读取文件

<!ELEMENT>

作用：定义 XML 标签允许包含什么内容，做结构校验，没有读取文件能力 语法示例：

含义：<ctfshow>标签里面只能放文本（#PCDATA = 可解析字符数据）。 只能规定标签结构，不能读取本地文件，没有 SYSTEM 关键字。

简单理解：

  • <!ELEMENT>：规定标签长啥样（校验）
  • <!ENTITY>：定义实体变量（XXE 利用）

<!ENTITY> 和 <!ELEMENT> 都是 DTD 的声明，但作用天差地别，<!ELEMENT> 没法用来做 XXE 读取文件。

正常 vs XXE

  • 正常：客户端发送业务 XML，解析器只解析标签读取业务数据，不访问外部文件
  • 攻击：客户端发送带外部实体的恶意 XML；解析器加载外部实体，读取本地文件 / 访问内网

XXE

XXE（XML External Entity，XML 外部实体注入），属于XML 解析漏洞。应用程序在解析 XML 输入数据时，未禁用 XML 外部实体，导致攻击者可以构造包含外部实体引用的恶意 XML 文档，触发恶意行为。漏洞归类：OWASP Top10 旧版收录，属于不安全的外部引用。

XXE 根本原因是XML解析器默认允许外部实体引用和DTD处理，而开发者未能显式禁用这些危险功能。

原理 / 介绍

XML 支持实体机制，实体可以理解为 XML 里的变量。

  • 内部实体：在 XML 文档内定义。
  • 外部实体：通过SYSTEM关键字，从本地文件、远程 URL 加载内容。

解析 XML 时，如果解析器支持并开启外部实体，攻击者构造 XML payload，定义外部实体指向目标资源；XML 解析器会读取该资源，并把内容带入 XML 文档处理，最终资源内容会出现在响应、报错信息中，实现文件读取、内网探测等攻击。

出现位置（风险场景）

  1. 接收 XML 格式数据的接口：POST 请求 body 为 XML，如接口Content-Type: application/xml
  2. 文件上传：上传 XML 类型文件（如 docx、svg、pom.xml 等底层使用 XML 的文件）
  3. SOAP 协议接口（WebService，数据传输为 XML）
  4. 配置文件解析、后台导入功能，解析 XML 数据
  5. 支持 XML 的富文本、文档解析模块
  6. 小程序 / 前端提交 XML 数据到后端服务

产生条件

  1. 后端使用的 XML 解析器默认开启外部实体、DTD 解析
  2. 应用接收用户可控的 XML 输入（用户可以完整控制 XML 内容）
  3. 后端解析 XML 前没有过滤、禁用 DTD 与外部实体
  4. 解析器有权限访问本地文件系统 / 内网地址（网络层面可达）

缺一不可：只有可控 XML + 解析器启用外部实体，才存在 XXE 风险。

危害

  1. 读取本地任意文件：/etc/passwd、配置文件、密钥、数据库账号密码等
  2. 内网服务探测（SSRF）：扫描内网端口、访问内网服务，结合内网横向移动
  3. 服务器端请求伪造，访问内网接口
  4. DOS 拒绝服务：经典【十亿嘲笑】实体炸弹，递归实体耗尽内存，服务器崩溃
  5. 部分场景下可实现远程代码执行（较少见，依赖解析器特殊扩展）
  6. 信息泄露，获取敏感业务数据

防护原则

  1. 禁用 DTD 文档类型定义；无法完全关闭 DTD 时，禁用外部实体加载
  2. 使用安全配置的 XML 解析器，关闭外部实体、外部参数实体
  3. 不解析来自不可信用户的 XML 输入；优先改用 JSON 替代 XML 传输
  4. 输入过滤：黑名单过滤<!DOCTYPE、<!ENTITY、SYSTEM关键字（仅辅助，不可单独作为防护）
  5. 最小权限原则：XML 解析进程使用低权限账号，限制文件读取权限
  6. 内网网络隔离，限制服务器主动访问内网资源（缓解 XXE 带来的 SSRF）
  7. 升级 XML 解析库，修复解析器本身历史漏洞

利用方式

XML 实体：类似变量。&xxx; 引用实体；外部实体 (ENTITY SYSTEM) 可以读取本地文件、发起网络请求，这就是 XXE 的根源。

类别

语法引用外部的实体，而非内部实体，那么能写哪些类型的外部实体呢？主要的有file、http、https、ftp等等，当然不同的程序、不同 XML 解析引擎支持的不一样，在外部实体SYSTEM "协议://xxx"里支持哪些协议：

ibxml2（底层 C 库，PHP、Python 很多 XML 库底层都是 libxml2）

支持：file、http、ftp

  • file://：读取本地文件
  • http://：发起 HTTP 请求（可做 SSRF、OOB 盲 XXE）
  • ftp://：访问 ftp 资源

注意：libxml2 2.9.0 之后默认关闭外部实体，也就是我们刚才那道 PHP 靶场，代码手动libxml_disable_entity_loader(false)才打开。

PHP（基于 libxml2，额外新增 PHP 专属流包装器，这是 PHP XXE 最特殊的点）

  1. php://filter：读取 php 源码的核心协议，base64 编码，避免 php 代码直接执行看不到源码，就是咱们上一题用的 payload。
  2. compress.zlib / compress.bzip2：压缩流，可读取压缩文件、绕过部分过滤
  3. phar://：phar 协议，配合文件上传，可触发 phar 反序列化（常和 XXE 组合考点）
  4. glob://：目录遍历，列出当前目录文件（列出目录找 flag 名字）
  5. data://：内联数据，可构造内联实体，不用外部 dtd

一句话：PHP 的 XXE 玩法最多，就是因为自带一大堆额外协议。

Java XML 解析器

Java 独有重点：

  1. jar://：读取 jar 包内部文件，读取 jar 里面的资源
  2. gopher://：经典 SSRF 协议，老版本 Java 支持 gopher，内网攻击神器（表格带 *，高版本 Java 会移除 gopher 支持）
  3. netdoc：Java 老版本特有协议，类似 file
  4. mailto：邮件协议，几乎不用

Java XXE 非常适合 OOB 盲注、内网 SSRF，支持 https，能访问云元数据。
Java没有 php://filter，不要把 PHP 的 payload 直接搬去 Java 环境，无效。

.NET

file、http、https、ftp 比较干净，没有额外花哨协议，只能基础读文件、发起 http/ftp 请求。

有回显 XXE

适用场景：提交 XML，服务器解析后，页面 / 响应包会把 XML 里实体的内容返回。 payload 示例（读取/etc/passwd linux）

Windows 读取文件：

原理：解析 XML 时，解析器会读取file://协议指向的本地文件内容，替换&file;，服务器把替换后的结果返回给你。

Java 特有：Java 解析 XML 支持jar://，还可以用http://协议。

无回显 XXE（盲 XXE / Out-of-band OOB XXE）

场景：服务器接收 XML，解析成功但是不返回任何解析内容，没有直接回显，无法直接看到文件内容。 思路：让服务器读取文件，然后把文件内容外带到我们自己控制的服务器（DNS/HTTP 请求带出数据）。

带外 HTTP 外带（最常用，Java 环境常用）

需要自己搭建一个简易 web 服务（或者用 Burp Collaborator、ceye.io 这类 DNSlog 平台）

evil.dtd（放在你的 vps 上）

流程：
1、服务器解析 XML，请求拉取evil.dtd
2、读取本地文件/etc/passwd存到%file
3、发起 http 请求，把文件内容作为 GET 参数传给你的服务器，你在日志拿到内容

注意：很多环境下参数实体不能直接在主文档引用，必须拆分外部 dtd 文件，这是盲 XXE 关键点。

DNSlog 外带

文件内容放到子域名，通过 DNS 解析带出数据，适合 HTTP 被拦截的场景，Ceye 常用。

利用协议做 SSRF（XXE + SSRF）

当解析器支持 http 协议，可以让服务器向内网发起请求，访问内网服务：

  • 探测内网主机、端口
  • 访问内网接口、元数据（云服务器 metadata）

限制：部分解析器会限制 http 协议。Java XML 解析器支持，libxml 有版本差异。

其他利用方式

拒绝服务（Billion Laughs 十亿笑攻击，DOS）

很多 WAF 会拦截这个 payload，只做 DoS，拿不到数据

原理：递归实体无限膨胀，消耗服务器内存 CPU。

读取压缩包（Java 独有 jar 协议）

常见限制 & 绕过思路

  1. 过滤 DOCTYPE
    • 编码绕过：UTF-16 编码 XML，WAF 识别失败，后端解析器正常解析
  2. 过滤 ENTITYSYSTEM、SYSTEM
    • 换行、空格拆分标签
  3. 不允许外部 dtd，但支持参数实体：OOB 盲注
  4. 过滤 file://：部分解析器支持php://filter（仅 PHP 环境 XML 解析）

XXE 在不同语言的支持差异

  • Java：风险最高，老版本默认开启外部实体，支持 file/http/jar 协议，OOB 盲 XXE 很常见
  • PHP libxml：libxml 2.9.0 之后默认关闭外部实体，很难打；低版本可利用 php://filter 读取文件
  • Python xml：Python 标准库 xml 模块，从 2.7.1/3.2.1 开始默认防护，禁用外部实体，基本无法利用
