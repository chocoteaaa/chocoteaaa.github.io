我以前一直以为这个读 SSIT

前置

模版：就字面意思，可以理解为一段固定好格式，等着开发人员或者用户来填充信息的文件。通过这种方法，可以做到逻辑与视图分离，更容易、清楚且相对安全地编写前后端不同的逻辑。

模板引擎：实现网站界面和数据、业务与逻辑代码分离，提升开发效率，常用于生成 HTML。它有一套专属语法，把数据填充进模板，组合生成最终 HTML 页面返回浏览器。

模板是一套供程序解析的语法，用来将数据转为可视化页面，前端、后端都能使用：

  • 后端渲染：服务器解析模板、填充数据，把生成好的完整 HTML 发给浏览器展示。
  • 前端渲染：浏览器从服务端获取原始数据，在本地解析渲染成页面。

示例：模板<html><div>{$name}</div></html>，将name变量填充为navy，最终输出navy。 模板引擎一般还支持分支判断、循环迭代和内置函数。

SSTI

原理

SSTI（Server-Side Template Injection，服务端模板注入）：服务端接收用户可控输入，直接把用户输入当作模板代码渲染执行。模板引擎本身用于页面渲染，当未对用户输入做过滤，输入内容被模板引擎解析，而非单纯当作普通字符串输出时，就会触发模板注入，最终执行模板语法、任意代码，读取文件甚至执行系统命令。

当前使用的一些框架，比如 python 的 flask，php 的 tp，java 的 spring 等一般都采用成熟的的 MVC 的模式，用户请求先到 Controller 控制器，然后根据请求类型和请求的指令发送给对应 Model 业务模型进行业务逻辑判断，数据库存取，最后把结果返回给 View 视图层，经过模板渲染展示给用户。

那么，漏洞根源：服务端未处理恶意输入，直接将其作为模板内容。模板引擎编译渲染时，执行了用户插入的恶意语句，造成信息泄露、代码执行、GetShell 等危害，危害程度取决于模板引擎本身能力。

出现位置

1、页面自定义内容：自定义昵称、自定义欢迎语、自定义页面标题、自定义邮件模板
2、错误页面渲染：错误信息直接把用户输入塞进模板展示
3、生成动态文档：后端用模板动态生成 PDF、Word、邮件内容
4、路由 / 参数直接渲染：GET/POST 参数、Cookie 值直接传入模板渲染函数
5、部分低代码平台、页面可视化编辑功能，后台使用模板引擎解析用户配置

产生条件（缺一不可）

1、用户可控输入：攻击者可以控制传入模板的内容（GET/POST/Cookie 等）
2、后端使用模板引擎动态渲染
3、输入拼接进模板源码：输入是字符串拼接，不是通过模板变量传入渲染
4、模板引擎未对特殊模板语法做过滤 / 转义

危害

根据模板引擎能力不同，危害逐级上升：

1、信息泄露：读取环境变量、配置文件、源码、数据库账号密码
2、服务器端任意代码执行（RCE）：执行系统命令，是 SSTI 最严重后果
3、文件读写：读取服务器任意文件、写入 webshell
4、接管服务器：拿到服务器权限，横向移动，窃取业务数据

注意：不是所有 SSTI 都能 RCE，如部分 Java 模板沙箱限制，可能只能信息泄露。

防护原则

1、优先使用变量传参，禁止字符串拼接模板，把用户输入作为模板变量传入渲染函数，而不是拼接到模板字符串。
2、输入输出编码：对用户输入做转义，关闭模板引擎原生的语法解析。
3、最小权限原则：模板运行进程使用低权限账号，即使被利用也限制影响范围。
4、禁用危险函数：在模板引擎配置中，移除执行命令、文件读写的类 / 函数（沙箱加固）
5、输入白名单校验：用户输入只允许预期字符，拒绝{{ }} ${} <% %>这类模板标记
6、模板文件静态化：尽量预编译模板，不要动态构造模板内容
7、WAF 辅助：拦截模板注入特征 payload，仅作为补充手段，不能作为唯一防护

沙箱

沙箱就是一套隔离、受限的运行环境。程序 / 代码在沙箱里面跑，只能被允许做有限的事情，不能随便访问系统资源。

通用沙箱核心能力

1、权限限制：限制读写文件、网络访问、创建进程、调用系统 API
2、资源隔离：限制 CPU、内存，防止耗尽主机资源
3、行为监控：记录里面代码做了什么，一旦有危险行为拦截
4、销毁隔离：沙箱里产生的内容可以一键清空，不污染外面真实系统

Docker 容器，本质也是操作系统层面的轻量沙箱。

Thymeleaf 的表达式沙箱

Thymeleaf 沙箱，不是操作系统沙箱，是应用层的「表达式语法沙箱」。 它只针对 SpEL 表达式 做限制：当用户可控内容被当作 SpEL 表达式解析时，沙箱会拦截危险操作。做的两件核心事
1、黑名单拦截类：默认禁止直接使用java.lang.Runtime这类危险类，防止命令执行
2、关键字拦截：检测new关键字，不允许实例化新对象

Thymeleaf 沙箱只是代码层面的黑名单校验，不是强隔离，它只是字符串 / 语法检查，不是操作系统级隔离。这种黑名单很容易被语法变形绕过，也就是 CVE-2026-40478、CVE-2026-41901 等沙箱绕过漏洞。

举个例子

沙箱规则：禁止表达式里出现 new （new + 空格）

  • 攻击者输入：new java.lang.Runtime → 沙箱检测到new ，拦截
  • CVE-2026-40478 绕过：new\tjava.lang.Runtime（new 后面是 Tab，不是空格） 沙箱字符串匹配找不到new ，直接放行；但底层 SpEL 引擎把 Tab 当成空白，正常解析执行。 –> 沙箱的校验逻辑被绕过，防护失效。

Flask、Jinja2

Python 的 Jinja2（Flask下的Jinja2模板注入）很经典很老，但还是有必要了解一下。。。

Flask

Flask 是Python 语言的轻量级 WSGI Web 微框架（microframework），核心很小，只保留 Web 必需基础能力：路由、请求处理；底层依赖两个核心组件：Werkzeug（WSGI 工具库）、Jinja2（模板引擎），用于快速构建 Web 应用程序和 API。

而 flask 也是 ssti 漏洞的常见来源

Jinja2

Jinja2 是Python 实现的模板引擎，常和 Flask 搭配使用。作用：把模板文件（HTML）、XML、配置文件等文本内容和后端传入的数据合并，生成最终返回给浏览器的网页。

Jinja2 使用 {{name}}结构表示一个变量，它是一种特殊的占位符，告诉模版引擎这个位置的值从渲染模版时使用的数据中获取。即{{ 变量 }} 输出内容

Jinja2 模板同样支持控制语句，像在{%…%}块中使用if语句。即{% 逻辑代码 %} 写分支 / 循环。

Flask 模板渲染函数

Flask提供两个模版渲染函数render_template()和render_template_string()。

其中render_template是用来渲染一个指定文件的。render_template_string()则是用来渲染字符串 的。

而渲染函数在渲染的时候，往往对用户输入的变量不做渲染，即：{{}}在 Jinja2 中作为变量包裹标识符，Jinja2 在渲染的时候会把{{}}包裹的内容当做变量解析替换。

比如{{2*2}}会被解析成4。因此才有了现在的模板注入漏洞。往往变量我们使用{{恶意代码}}。正因为{{}}包裹的东西会被解析，因此我们就可以实现类似于 SQL 注入的漏洞

本质：顺着函数向上拿到它的模块全局命名空间，如：

1、lipsum是 Jinja2 模板内置全局函数，原生作用：生成 Lorem Ipsum 占位假文本（排版测试用的无意义拉丁文填充文字），在 Flask+Jinja2 环境默认直接可用，lipsum 本身就是函数对象 → 直接访问.__globals__。

定位：不是独立入口，更多是前两条路径里面的 “逃生舱”，即 1、2 拿到字典后，若找不到 os，就去__builtins__里面捞危险内置函数。
