接口

Interface

在前面我们知道，抽象类的抽象方法定义了接口规范，即规定高层类的接口，保证了所有子类都有相同的接口实现，这样才能体现多态价值。

那么如果一个抽象类没有字段，所有方法全部都是抽象方法：

那么我们可以直接把这个抽象类写为接口：interface，使用它来声明一个接口。

事实上，使用interface的接口，接口默认里面的抽象方法都是 public abstract，只不过可以省略不写，因为它是比抽象类还要抽象的纯抽象接口，所以连字段都不能有。（写不写效果都一样）

接口继承

interface使用extends继承另一个interface。

在Java中，一个类只能单继承，不能从多个类继承；但是接口能多继承，继承自多个接口。

子接口会把父接口所有抽象方法都继承下来；实现子接口的类，必须实现全部来自父接口 + 子接口的抽象方法。

继承关系

一般来说，公共逻辑适合放在 abstract class（抽象类）中，把多个子类重复的字段、通用方法抽出来；差异化的具体逻辑交给各个子类重写。 而 interface（接口），用来定义能力契约，代表 “这个对象具备什么行为”，用来表达抽象的能力层次

1、抽象类（abstract class）：承载公共代码，解决复用问题 抽象类本质还是类，可以有成员变量、构造方法、普通实例方法。 如果多个子类有大量重复的代码（共同属性、通用逻辑），就抽到抽象父类，子类直接继承复用，不用重复抄写。 抽象类里的抽象方法，则用来强制子类补齐各自独有的差异化逻辑。
2、接口（interface）：承载能力契约，定义 “能做什么” 接口不适合存放大量共用的成员状态，核心是定义一套行为标准。 接口之间可以用extends做多继承，用来分层描述能力；类通过implements实现接口，代表这个类拥有该接口约定的能力。 接口关注的不是 “它是什么”，而是 “它能完成哪些动作”。

那么，这样合理设计 interface 和 abstract class 的继承关系，就可以充分复用代码。

在使用的时候，实例化的对象永远只能是某个具体的子类，但有了接口之后，我们更倾向用接口类型去引用对象，而不是像之前面向抽象编程那样，通过抽象类Cat类型去引用具体子类。因为接口比抽象类更加抽象，它只约定能力，不绑定事物本身的类型，耦合度更低。

面向抽象编程不止有抽象类这一条路。有接口之后，优先用接口类型引用对象，而不是抽象类Cat。 因为接口只约定“能力”，不限制它属于哪一类事物，解耦程度更高。

default方法

注意：default 方法写在 interface 里面，用 default 关键字修饰。用来取消强制重写的

Java 8 之前，接口里全部都是抽象方法。一旦接口新增抽象方法，所有已经实现这个接口的类全部都要改动、重写新方法，否则编译报错。

default 方法就是用来解决这个问题：在接口里提供方法的默认实现，实现类可以直接继承这个默认逻辑，不强制重写；如果需要自定义，也可以选择覆写。

不知道为什么要加这句话：default方法和抽象类的普通方法是有所不同的。因为interface没有字段，default方法无法访问字段，而抽象类的普通方法可以访问实例字段。

静态字段&方法

字段

在一个class中定义的字段，我们称之为实例字段。用static修饰的字段，称为静态字段：static field。

静态属于类本身，不属于某个对象实例；实例成员属于单独的对象

普通成员变量：每 new 一个对象，就独立拥有一份。
静态字段：归这个类所有，全类只有一份，所有对象共享。

特点：

  • 随着类加载时初始化，不需要 new 对象就能访问
  • 所有实例共用同一份，一处修改，全部可见

静态字段并不属于实例，无论修改哪个实例的静态字段，效果都是一样的：所有实例的静态字段都被修改了。

因此，不推荐用实例变量.静态字段去访问静态字段，因为在Java程序中，实例对象并没有静态字段。在代码中，实例对象能访问静态字段只是因为编译器可以根据实例类型自动转换为类名.静态字段来访问静态对象。

推荐用类名来访问静态字段。可以把静态字段理解为描述class本身的字段。所以我们不用c1.count，而用Cat.count。

方法

用static修饰的方法称为静态方法。调用实例方法必须通过一个实例变量，而静态方法可以直接 类名.方法() 调用，不用创建实例。静态方法同样属于类，不属于对象。

注意：静态方法里面，不能直接使用 this，也不能直接访问实例字段、实例方法（因为调用静态方法时，不一定存在对象）。

静态方法类似其它编程语言的函数。例如：

静态方法没有多态，不存在动态绑定；看引用类型，不看实际对象。静态方法经常用于工具类。例如：Arrays.sort()、Math.random()

静态方法也经常用于辅助方法。注意到Java程序的入口main()也是静态方法。

接口的静态字段

我们前面讲了接口interface是一个纯抽象类，所以它不能定义实例字段。但是，interface是可以有静态字段的，并且静态字段必须为final类型。

即，Java 接口里定义的字段，**默认都是 public static final**，你不写修饰符，编译器也会自动补上。

  • public：所有地方都能访问
  • static：属于接口本身，不属于实现类的对象，不用 new 对象就能访问
  • final：常量，赋值之后不能修改

所以接口中的字段本质就是常量。

关键点

  1. 必须在定义时直接赋值，不能留空，也不能在实现类构造器里赋值；
  2. 实现类可以直接继承使用这个常量，但不能修改；
  3. 就算多个接口有同名常量，实现类直接使用时会编译报错，需要写接口名.常量名区分。

对比类里的静态变量

普通类的静态字段：可以是变量（可修改），修饰符需要手动写； 接口的字段：强制 public static final，只能是常量。

包（package）

在前面的代码中，我们把类和接口命名为Cat、Siamese、Ragdoll这类简单名字。 在现实中，如果小明写了一个Cat类，小红也写了一个Cat类，现在，小白既想用小明的Cat，也想用小红的Cat，怎么办？ 如果小军写了一个Cat类，项目里其他地方也有一个Cat类，如何解决类名冲突？

在 Java 中，我们使用package来解决名字冲突。 Java 定义了一种名字空间，称之为包：package。一个类总是属于某个包，类名（比如Cat）只是一个简写，真正的完整类名是包名。类名。

例如： 小明的Cat类存放在包ming下面，因此，完整类名是ming.Cat； 小红的Cat类存放在包hong下面，因此，完整类名是hong.Cat； 小军的Cat类存放在包mr.jun.animal下面，因此，完整类名是mr.jun.animal.Cat；

在定义 class 的时候，我们需要在第一行声明这个 class 属于哪个包。

在Java虚拟机执行的时候，JVM只看完整类名，因此，只要包名不同，类就不同。

包可以是多层结构，用.隔开。例如：java.util。所有Java文件对应的目录层次要和包的层次一致。

使用的时候有两种方式：

  1. 用import导入其中一个，直接简写Cat；
  2. 两个都要用，就写完整类名区分。

Import

当我们只需要使用某一个包里面的类时，就可以用import语句把类引入当前代码，之后就不用每次都写冗长的完整类名，直接用简单类名即可。

import支持两种写法：

  1. 精确导入：import ming.Cat;，只导入这一个类，推荐日常开发使用；
  2. 通配导入：import ming.*;，导入ming包下所有类，可读性弱，正式项目一般不推荐。

注意：import只是告诉编译器，当你写简写类名Cat时，优先去哪个包找这个类，不是把类的代码复制进来。

有一个特殊的包：java.lang，这个包下的基础类（String、Object、Integer等）会自动默认导入，不需要我们手动写import java.lang.String;。

自动导入的是java.lang包，但类似java.lang.reflect这些包仍需要手动导入。

如果有两个class名称相同，例如，mr.jun.Arrays和java.util.Arrays，那么只能import其中一个，另一个必须写完整类名。（详细信息可见附上的文章）

但要记住一条：如果同时导入两个包的同名类，编译器不知道你指的是哪一个，代码直接报错。这种情况就不能依赖import简写，只能始终写完整类名ming.Cat、hong.Cat来区分。

方法参数

最佳定义方式

如果不确定是否需要public，就不声明为public，即尽可能少地暴露对外的字段和方法。

把方法定义为package权限有助于测试，因为测试类和被测试类只要位于同一个package，测试代码就可以访问被测试类的package权限方法。

一个.java文件只能包含一个public类，但可以包含多个非public类。如果有public类，文件名必须和public类的名字相同。

Final

再提一提，用final修饰class可以阻止被继承，用final修饰method可以阻止被子类覆写，用final修饰field可以阻止被重新赋值，用final修饰局部变量可以阻止被重新赋值。

内部类

Java 允许在一个类的内部再定义类，放在里面的类叫做内部类（嵌套类），外层的类叫外部类。 内部类分为 4 种：静态内部类（静态嵌套类）、成员内部类（非静态内部类）、局部内部类、匿名内部类。

核心特点：内部类可以访问外部类的 private 成员（私有属性、私有方法），编译器把外部类和它的内部类看作同一个访问单元。

成员内部类（Inner Class）

写在外部类里面、方法外面，不加static。

  • 必须先创建外部类实例，再用外部类对象创建内部类对象
  • 自带隐式引用外部类.this，可以直接访问外部类所有成员，包括实例 private 成员

区分重点：成员内部类依附外部对象；静态内部类不依附外部对象。

和普通类对比，内部类有一个特殊权限：可以访问外部类的私有字段、私有方法。 编译器把外部类和它的成员内部类当成同一个作用域，即使是private的成员，内部类也能读写。

静态内部类（Static Nested Class）

用static修饰的内部类，属于外部类本身，不属于外部类的实例对象。

  • 不需要先创建外部类对象，就能直接 new 静态内部类
  • 只能访问外部类的static 静态成员，不能直接访问外部类的实例成员

用static修饰的内部类和Inner Class有很大的不同，它不再依附于Outer的实例，而是一个完全独立的类，因此无法引用Outer.this，但它可以访问Outer的private静态字段和静态方法。如果把StaticNested移到Outer之外，就失去了访问private的权限。

定义在方法 / 代码块里面，作用域仅限于当前{}代码块，出了方法就不能用。

Classpath&jar

classpath

classpath 是 JVM 查找 .class 文件的路径列表。

我们写好的 .java 源代码，编译后会生成 .class 字节码文件，这才是 JVM 真正能执行的代码。运行 java 命令时，JVM 需要知道去哪里加载这些 .class 文件——classpath 就是告诉 JVM 搜索路径的配置。

有了 classpath，JVM 就能明白：当代码中出现 abc.xyz.Hello 这个类时，应该到哪些目录下查找对应的 Hello.class。

IDE 与核心库

在 IDE 中直接运行 Java 程序时，IDE 会自动帮我们构造 -cp 参数，把项目的编译输出目录、引入的所有 jar 包都包含进去，因此我们通常感觉不到 classpath 的存在。

另外，我们的代码经常用到 Java 核心库的类（如 String、ArrayList）。有些教程会说要把 JVM 自带的 rt.jar 加进 classpath——实际上完全不需要。JVM 内置了核心类库的加载机制，与 classpath 无关。

注意：不要把 Java 核心库加入 classpath！很多简单场景下，默认的 .（当前目录）就足以运行程序。

jar

如果编译产生了大量 .class 文件，散落在各层目录中，管理起来肯定很麻烦。要是能把整个目录”打包”成一个文件，备份、分发就方便多了——jar 包就是干这件事的。

jar 包可以把 package 组织的目录层级，以及各目录下的所有文件（包括 .class 文件和其他资源文件）打包成一个文件。无论是备份还是发给别人，都简单得多。

jar 包的本质：一个特殊的 zip 文件

jar 包实际上就是 zip 格式的压缩文件，它本身相当于一个目录。要运行 jar 包里的类，直接把 jar 文件加入 classpath 即可：

JVM 会自动在 hello.jar 内部搜索需要的类，无需解压。

如何创建 jar 包

既然 jar 就是 zip，最简单的办法是：在资源管理器中找到正确的目录，右键选择”发送到”→”压缩 (zipped) 文件夹”生成 zip，再把后缀 .zip 改成 .jar 即可。

MANIFEST.MF：jar 包的”说明书”

jar 包内部可以包含一个特殊文件：META-INF/MANIFEST.MF。它是纯文本格式，可以指定 Main-Class 等信息。JVM 会自动读取它——只要配置了 Main-Class，运行时就不用在命令行手动写类名：

实际开发：交给构建工具

在大型项目中，没有人会手写 MANIFEST.MF、手动压缩打包。Java 生态有丰富的构建工具（如 Maven、Gradle），一条命令就能自动编译、打包、生成带 Main-Class 的 jar，配合classpath管理，整个流程完全自动化。
