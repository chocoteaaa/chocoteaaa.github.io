基础

原理及分类

RCE 远程代码执行（Remote Code Execution）攻击者无需本地访问，就能在目标服务器 / 主机上执行任意代码、系统命令的高危漏洞，属于最高危漏洞类别之一，OWASP Top10 里的注入类漏洞。漏洞成因核心一句话：存在开发人员使用的一些危险函数，程序把用户可控的外部输入，直接当作「系统命令」或「程序代码」交给解释器执行，没有做安全校验。

分为远程命令执行（Command Injection，命令注入）执行系统原生命令（shell 命令） 攻击者远程执行目标系统的系统命令（如Linux的ls、cat命令，Windows的dir、ipconfig命令），多用于获取系统信息、遍历文件、创建后门等基础操作典型场景：Web应用中命令拼接未过滤、系统调用函数未校验输入。例子：

PHP：system() / exec() / shell_exec() / passthru()
Python：os.system() / os.popen()
Java：Runtime.getRuntime().exec(String)

和远程代码执行（Code Injection，代码注入）直接注入编程语言代码（如PHP、Python、Java代码），由程序解释器执行，不是系统 shell 命令，可实现更复杂的操作（如植入木马、反弹shell、控制整个服务器）。典型场景：代码执行函数未过滤恶意代码、序列化漏洞导致代码执行（如 PHPeval会直接把字符串当成PHP代码执行）。常见场景：

PHP：eval()、assert()
Python：exec()、eval()
NodeJS：eval()、new Function()

漏洞产生位置

狭义 RCE：业务代码直接可控输入，执行编程语言代码 / 操作系统命令（CTF PHP 无参数 RCE、命令注入都属于这类）
广义 RCE：各类漏洞最终效果达到远程代码执行，漏洞根源不在基础命令 / 代码执行函数上

一、狭义 RCE 产生位置

  1. 系统命令拼接点（命令注入） 外部输入直接拼接到 shell 命令，送入系统命令执行函数。 示例：PHP system()、Python subprocess(shell=True)、Java Runtime.exec()
  2. 动态代码执行点（代码注入） 外部输入直接当作编程语言代码交给解释器执行。 示例：PHP eval()、可变函数；Python exec()；JS new Function()

共同点：漏洞来自开发者编写的业务代码，直接使用危险执行函数接收外部可控输入。

二、广义 RCE 产生位置（漏洞最终结果为 RCE，但底层不是 eval/system 这类函数）

  1. 第三方组件、框架漏洞 Log4j2、Spring4Shell、Shiro，漏洞在引入的框架 / 依赖库，业务代码本身没写危险执行函数。
  2. 模板引擎（SSTI 模板注入） Jinja2、Thymeleaf 等模板引擎解析用户可控输入，触发代码执行。
  3. 反序列化漏洞 PHP unserialize()、Java 反序列化、Python pickle，恶意序列化对象触发代码执行。
  4. 文件上传 + 解析漏洞 上传脚本文件，中间件错误解析文件，执行脚本代码；路径穿越常作为前置漏洞配合使用。
  5. 内存破坏类漏洞（客户端 RCE） 如 CVE-2026-85046，浏览器 V8 引擎、Office 解析器，解析恶意内容造成内存破坏，最终实现 RCE。

和其他漏洞简单区分

  • RCE：执行系统命令 / 代码，拿到服务器执行权限
  • SQL 注入：操作数据库，只能读写数据库，一般不能直接执行系统命令
  • XSS：在浏览器执行 JS，是客户端漏洞，不是服务器 RCE
  • SSTI：模板注入，属于代码执行，归类广义 RCE
  • 路径穿越 + RCE：路径穿越仅能读写文件，整条利用链配合达成 RCE 效果，归类广义 RCE
  • 不安全反序列化：传入恶意序列化数据触发魔术方法 /gadget 链，利用成功可执行代码，归类广义 RCE
  • 第三方组件漏洞：组件解析特殊数据包触发缺陷，利用成功可远程执行代码，归类广义 RCE

不安全反序列化、模板注入SSTI、第三方组件漏洞（Log4j2、Spring4Shell）这类漏洞原理不属于传统的命令 / 代码注入，但是漏洞利用成功最终效果是 RCE（远程代码执行），因此安全领域习惯称之为广义 RCE，这里只围绕RCE经典的两种方式（狭义）记录，剩余的作为单独漏洞后续单开更新。

危害

RCE漏洞之所以被列为高危漏洞，核心在于其攻击成本低、危害后果严重，主要体现在三个方面：
1、攻击门槛低：无需复杂的技术储备，借助AI工具（如2026年主流的RCE漏洞扫描工具、Payload生成工具），新手也能快速利用已知RCE漏洞发起攻击；
2、危害范围广：可影响Web应用、服务器、物联网设备、工业控制系统等各类场景，一旦触发，攻击者可完全控制目标系统，窃取敏感数据、植入勒索软件、发起横向渗透；
3、难以快速处置：部分RCE漏洞利用后会删除日志、隐藏进程，导致安全人员难以溯源攻击源头，且漏洞修复需兼顾业务兼容性，修复周期较长。

下面写出各类语言的危险函数，包含广义狭义：

PHP

命令执行（调用系统 shell，都可套在eval中）

  1. system(string $command)：执行系统命令，输出命令结果，返回最后一行输出
  2. exec(string $command)：执行命令，不直接输出，结果存入第二个参数数组，返回输出最后一行
  3. shell_exec(string $cmd)：执行 shell 命令，返回完整字符串结果；无输出返回 null
  4. passthru(string $command)：执行命令，直接把原始二进制输出输出到页面（适合二进制回显）
  5. popen() / proc_open()：创建进程执行命令，打开管道读写结果
  6. pcntl_exec() ： 在当前进程空间执行指定程序，当发生错误时返回 false ，没有错误时没有返回。
  7. `（反引号）：同 shell_exec()

代码执行（解析 PHP 代码）

  1. eval(string $code)：最经典，将字符串作为 PHP 代码执行，末尾必须带分号 ;
  2. assert()：旧版 PHP 可当作 eval 用，传入字符串会执行 PHP 代码（PHP7.2 后废弃此能力）
  3. create_function()：创建匿名函数，字符串参数会被解析为代码（PHP7.2 移除）

额外高危：文件包含 include / require / include_once，包含用户可控文件，文件内 PHP 代码会执行（LFI/RFI，间接 RCE）

Python

命令执行（调用系统 shell）

  1. os.system(cmd)：执行 shell 命令，直接输出到终端，返回退出状态码

  2. os.popen(cmd)：执行 shell 命令，返回文件对象可读结果

  3. subprocess.call(cmd, shell=True)/subprocess.run(cmd, shell=True)/subprocess.check_output()

    ——危险写法：传字符串 subprocess.call("ping "+ip, shell=True)（按 shell 解析字符串）

    ——安全写法：传列表 subprocess.call(["ping",ip])，shell=False 不会启动 shell，无法注入

  4. commands.getoutput(cmd)：Python2 专用，执行并返回输出字符串

代码执行（解析 Python 代码）

  1. eval(str)：将字符串作为表达式求值并返回结果（不能执行语句）
  2. exec(str)：最经典，将字符串作为代码块执行，无返回值
  3. compile(str, filename, mode)：编译字符串为代码对象，常与 exec/eval 配合
  4. pickle.loads(bytes)：反序列化字节流，触发对象 __reduce__ 等魔术方法，可造成 RCE
  5. yaml.load(stream)：PyYAML 旧版不安全，可构造恶意对象执行代码（应用 safe_load）

Java

企业级应用重灾区，Java 很少直接写 eval 类函数，RCE 大多来自Runtime.exec、反序列化、JNDI 注入

命令执行

  1. Runtime.getRuntime().exec(cmd)：执行命令；只按空格拆分

    ——传入字符串时会启动 shell，可命令注入；复杂 shell 语法失效（常见绕过点，但需配合其他技巧）

    ——传入字符串数组则安全，不会解析管道、分号等特殊符号

  2. ProcessBuilder(cmdList).start()：可执行命令，传列表可精确控制参数

代码执行 / 反序列化

  1. ScriptEngine.eval(str)：脚本引擎执行 JS/Groovy 等代码字符串
  2. SpringExpressionParser.parseExpression(str).getValue()：SpEL 表达式求值，历史上多个 Spring 高危 RCE 源于此
  3. ObjectInputStream.readObject()：Java 原生反序列化，配合依赖中的 gadget 链触发 RCE（Fastjson、Shiro、WebLogic 等重灾区）
  4. XMLDecoder.readObject()：JDK 自带 XML 反序列化，可直接执行任意代码，极危险
  5. Class.forName() + newInstance()：动态加载并实例化类，配合可控类名/路径可 RCE
  6. JndiTemplate.lookup() / InitialContext.lookup()：JNDI 注入，可加载远程恶意类（Log4j2 漏洞核心）

注意：Java 本身没有像 PHP eval 那样直接执行字符串代码的内置函数。

Node.js

命令执行

  1. child_process.exec(cmd, cb)：启动 shell 执行命令，结果在回调中返回
  2. child_process.execSync(cmd)：同步版本，直接返回输出字符串
  3. child_process.execFile() / spawn()：默认不经过 shell，相对安全

代码执行 / 反序列化

  1. eval(str) / new Function(str)()：字符串作为 JS 代码执行，与浏览器 eval 同性质
  2. setTimeout(str) / setInterval(str)：参数为字符串时隐式 eval
  3. vm.runInContext(str, sandbox)：在指定上下文执行代码，vm 不是安全沙箱，逃逸公开已久
  4. node-serialize 的 unserialize()：该库会还原函数对象，直接 RCE（npm 上著名问题库）
  5. require() 加载用户可控路径的模块文件

Node 额外考点：原型链污染，配合上面函数实现 RCE

C / C++（底层与缓冲区溢出结合）

命令执行

  1. system(cmd)：调用 /bin/sh -c 执行命令，返回退出状态
  2. popen(cmd, mode)：执行命令并打开管道读写其输入/输出
  3. exec*() 族（execl/execv/execvp 等）：替换当前进程映像执行新程序
  4. ShellExecute() / WinExec()：Windows 下执行程序或打开文件

代码执行 / 内存类

  1. dlopen(path) / LoadLibrary(path)：加载动态库，库文件构造器即执行代码
  2. strcpy / sprintf / gets：不检查边界的字符串函数，缓冲区溢出可覆盖返回地址劫持控制流（经典二进制利用入口）

Ruby

命令执行

  1. system(cmd) 字符串形式：经过 shell；数组形式 system("cmd", "arg") 不经过 shell
  2. 反引号 cmd：执行 shell 命令，返回标准输出
  3. %x{cmd}：与反引号等价
  4. Kernel.spawn(cmd) / exec(cmd)：创建或替换进程执行命令

代码执行 / 反序列化

  1. eval(str)：执行 Ruby 代码字符串
  2. ERB.new(template).result：渲染 ERB 模板，模板内容即为 Ruby 代码（模板注入直接 RCE）
  3. Marshal.load(data)：反序列化 Ruby 对象，类加载过程可执行代码
  4. YAML.load(data)：旧 Psych 版本可构造恶意对象执行任意代码

C# / .NET

命令执行

  1. Process.Start(startInfo)：UseShellExecute=true 时经 shell 解析；ArgumentList 逐项传参较安全
  2. PowerShell.Create().AddScript(str).Invoke()：执行 PowerShell 脚本字符串

代码执行 / 反序列化

  1. BinaryFormatter.Deserialize(stream)：最危险的反序列化器，微软官方建议淘汰，配合 gadget 直接 RCE
  2. Assembly.Load(bytes).CreateInstance(typeName)：加载字节数组中的程序集并实例化
  3. XamlReader.Parse(xaml)：解析 XAML 可实例化任意类型（如 ObjectDataProvider 调方法）
  4. JavaScriptSerializer / Newtonsoft TypeNameHandling.All：反序列化时解析类型名可指定恶意类

Shell / Bash

  1. eval str：把字符串当 shell 命令二次解析（嵌套 eval 是经典提权链一环）
  2. source file / . file：在当前 shell 上下文执行文件内容
  3. exec cmd：用命令替换当前 shell 进程
  4. $() / 反引号命令替换：本身正常，但替换内容来自可控输入时会级联执行

模板引擎（SSTI 类，提一下）

  1. Python Jinja2：Template(source).render()，模板字符串可控即 Python RCE
  2. Java Freemarker：Template.process()，new 指令与内建函数利用
  3. PHP Smarty：fetch("string:...") / {php} 标签（旧版）
  4. Ruby ERB、Node EJS/Pug、.NET Razor：原理相同——模板即代码，可控模板源即 RCE

审计要点：每个语言都遵循同一模式——用户输入 → 字符串拼接/反序列化 → 解释执行。CTF 中 PHP 考 eval/assert/preg_replace /e 最密集；真实攻防中 Java 反序列化和 Node/Python 的 pickle/node-serialize 类依赖漏洞占比最高。

使用条件：当请求头中有cookie时（或者自己手动添加cookie头也行）
原理核心：
1、session_start()：开启 PHP 会话，初始化 session；
2、session_id()：读取当前 Session 的 ID 字符串；
3、PHPSESSID 的值由请求 Cookie 可控，我们抓包修改请求头 Cookie 里PHPSESSID=flag.php；
4、session_id()就会返回我们设置的字符串flag.php；
5、把session_id()的返回值，直接传给文件读取函数highlight_file()，实现读取文件。

逐层拆解：
1、session_start()：开启 session，返回布尔值true；
2、session_id()：读取 Cookie 里PHPSESSID的值；
3、highlight_file("flag.php")：读取文件。

注意：session_start()返回 true，但作为 session_id 参数时，session_id () 不带参数读取当前会话 id，PHP 特性。

使用步骤：
1、提交 payload：?code=highlight_file(session_id(session_start()));
2、抓包，在 HTTP 请求 Cookie 添加：PHPSESSID=flag.php
3、发送请求 → session_id()返回flag.php，读取 flag 文件。

如果想读取其他文件，只需要修改 Cookie 里 PHPSESSID 的值： PHPSESSID=etc/passwd → highlight_file('etc/passwd')

1、可以自定义任意字符串，目录遍历只能列出当前目录已有文件；session 路线你想传入什么文件名，直接改 Cookie 的 PHPSESSID 即可。
2、不受 scandir/glob 禁用影响 当scandir、glob全部被 ban，目录遍历路线废掉，session 路线是首选兜底方案。
3、有长度 / 字符限制 PHPSESSID
4、默认只能是字母、数字，部分环境不允许/，此时无法读取绝对路径文件，只能读取当前目录文件。（部分 php.ini 配置限制 sessionid 字符集，不能用/、.以外特殊字符，这是最常见坑。）
5、函数同样受disable_functions管控 如果session_start()、session_id()被禁用，这条路线直接失效。
6、受open_basedir限制 就算拿到字符串/etc/passwd，open_basedir 拦截的话依然读不了。

RCE的防护

简单提一提防护以及现状。

1. 代码层（根源防护，最重要）

1、尽量不使用危险执行函数 PHP：避免 eval、assert、system、shell_exec、exec、passthru、可变函数调用。

php.ini disable_functions 禁用高危函数，抑制 RCE 利用。

2、用户输入白名单校验，不信任外部输入 只允许业务预期字符，优先白名单，黑名单容易被绕过。
3、命令执行必须使用安全转义 / 参数化调用 escapeshellarg() / escapeshellcmd()；禁止直接拼接用户输入到 shell 命令。

推荐参数数组调用，杜绝字符串拼接。

4、禁止可控输入直接作为函数名（防御可变函数 RCE）
5、反序列化：使用类白名单校验，签名，尽量不使用 unserialize。

2. PHP 配置加固

1、open_basedir：限制 PHP 能访问的目录，就算 RCE 成功，也不能跨目录读文件。
2、关闭不必要危险配置：allow_url_include=Off
3、限制 session 相关配置，限制 PHPSESSID 可用字符，防御 session 路线无参数 RCE。

3. 服务器 / 系统层面

1、最小权限原则：web 进程使用普通用户（www-data）运行，禁止 root，降低危害。
2、及时更新框架、第三方组件补丁（Log4j2、Spring4Shell 这类组件 RCE）。
3、网络隔离：限制服务器主动外连，防止 DNSlog 反弹 shell。

4. 安全设备与运行防护

1、WAF：拦截 RCE 特征 payload（payload 字符串、命令分隔符;|&），缺点容易编码绕过。
2、RASP：运行时检测危险函数调用，防御无参数这类 WAF 难识别的 RCE。
3、日志审计：记录命令执行、文件读取行为，发现攻击。

RCE现代状况

基于 2025–2026 年的最新数据，RCE 的现代状况可以概括为一句话：RCE 没有变少，而是变得更快、更前置、更集中于边缘设备和供应链。”发现漏洞→被打穿”的时间窗口已经坍塌，防御逻辑从”打补丁”被迫转向”假设已被 RCE，限制其后果”。

一、时间窗口坍塌：从 756 天到 4 小时

漏洞披露到被利用的平均间隔：

年份 披露→利用平均时间
2018 756 天
2021 84 天
2023 6 天
2024 约 4 小时（最快观测值）
2025 常在披露前（零日）

2025 年的具体数据：28% 的漏洞在披露后 1 天内遭利用，28.96% 的 KEV 漏洞在 CVE 发布当天或之前就被利用（2024 年为 23.6%），而厂商平均需要 15 天才能推出补丁。补丁永远追不上利用，”补丁窗口”概念已名存实亡。

二、零日化：2026 年被利用漏洞中 67.2% 是零日

2018 年这一比例仅为 16.1%。攻击者不再等补丁后再逆向 N-day，而是直接囤零日、或通过供应链（源代码窃取）自己挖。最典型案例：F5 BIG-IP CVE-2025-53521——Mandiant 追踪的 UNC5221 潜伏 F5 内网约 12 个月偷走 BIG-IP 源码，挖出的漏洞 2025 年 10 月披露时被定级为 DoS（CVSS 8.7），2026 年 3 月重新定级为 RCE（CVSS 9.8）并确认在野利用——大量机构以为自己在防”崩溃 bug”，实际在打 RCE 补丁。

三、规模与构成：命令注入仍是 RCE 之王

  • CISA KEV 目录 2025 年底达 1,484 条，全年新增 245 条（20% 增速，三年最大）；
  • 2025 年 KEV 新增中最常见的弱点类型：CWE-78 OS 命令注入第一（18 个）、CWE-502 反序列化第二（14个）、CWE-22 路径穿越第三、CWE-416 UAF 第四、CWE-94 代码注入新上榜；
  • 执行层面数据：2025 年被利用的漏洞中 69% 无需认证，约 30% 直接造成 RCE。

注意：真实世界统计里”开发手写的 eval($_POST)“占比并不高——占大头的是 C 语言内存破坏（UAF/OOB）和反序列化，这与前面我们讲的 PHP CTF 世界是两个生态。

四、重灾区分布（2025–2026 的代表性在野 RCE）

1. 边缘设备/网关仍是头号入口

VPN、ADC、防火墙类设备反复成为勒索软件初始入口：Ivanti Connect Secure 栈溢出无认证 RCE（CVE-2025-22457，EPSS 约 99.98%）、CitrixBleed 2、Fortinet/SonicWall 认证绕过、F5 BIG-IP、WatchGuard（7.5 万台暴露）。共同特征：内存破坏 + 无认证 + 暴露公网。

2. AI 基础设施成为新大陆

  • React2Shell（CVE-2025-55182，CVSS 10.0）：React Server Components 无认证 RCE，EPSS 100%，已被用于勒索软件和挖矿；
  • Langflow（CVE-2025-3248，CVSS 9.8）：AI 工作流平台无认证代码注入；
  • Ray（CVE-2025-62593，CVSS 9.4）：因长期不给关键端点加认证，被 DNS rebinding 打浏览器侧 RCE，2026 年 8 月入 KEV。

共同教训：AI 工具链部署快、硬化少、默认无认证。

3. 企业软件供应链

SAP NetWeaver 文件上传→webshell（CVSS 10.0，零日在野）、GoAnywhere MFT 反序列化（CVSS 10.0，勒索软件初始访问）、Cleo 文件上传、Erlang/OTP SSH 守护进程预认证 RCE（CVSS 10.0）、Roundcube/Craft CMS、Commvault、Git 客户端（CVE-2025-48384，CI/CD 场景）。

五、防御范式的实际转变

数据支撑了几个已经落地的趋势：

  1. 优先级从 CVSS 转向 EPSS/KEV：漏洞太多（每天 130+ 新 CVE），人工分诊失效；且 KEV 本身滞后于现实——H1-2025 实际在野利用比 KEV 记录还多。
  2. 虚拟补丁/WAF 应急规则成为披露日（0-day）到补丁日（15 天）之间的唯一屏障。
  3. **从”防 RCE”转向”容忍 RCE”**：运行时层做系统调用管控（syscall mediation）、身份层做 JIT 审批与事务限额、数据层做分片/令牌化——即使 RCE 成功也把破坏压缩到分钟级、单点级。
  4. 出网管控成为高 ROI 控制项：大量在野利用链依赖反弹连接/C2，egress filtering 能直接打断。
