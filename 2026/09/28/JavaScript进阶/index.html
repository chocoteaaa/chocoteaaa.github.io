JSON 序列化与反序列化

前面我们在 BOM 本地存储中简单接触过 JSON.stringify 和 JSON.parse，但也仅临时使用未详细介绍。

对于Java 后端开发者来说：JSON 是前后端唯一通用的数据交互格式，是重中之重。

后端返回给前端的接口数据、前端传后端的参数、数据库存储的对象数据，几乎全部依赖 JSON 转换。

本文系统讲解 JSON 语法、JS 对象与 JSON 区别、序列化、反序列化、以及工作中 100% 会遇到的坑。

JSON 是什么

JSON（JavaScript Object Notation）：JavaScript 对象表示法，是一种纯文本数据格式。

核心特点：

  • 独立于语言：Java、JS、Python、Go 全部通用
  • 专门用于数据传输、数据存储
  • 无方法、无函数，只能存纯数据
  • 格式极其严格，错一个符号就报错

JSON 与 JS 对象的核心区别

很多人混淆 JS 对象和 JSON，二者完全不是一个东西：

  • JS 对象：JS 代码中的引用类型，可存属性、方法、任意值，属于代码对象
  • JSON：纯文本字符串，只能存数据，属于数据文本

JSON 强制语法规范（严格）

  • 所有 key 键名必须双引号（单引号、不写引号都不行）
  • 字符串值必须双引号
  • 不能有函数、不能有 undefined、不能有注释
  • 结尾不能有多余逗号

对比案例

  1. JS 对象（代码中使用，格式宽松）
  1. JSON 字符串（网络传输使用，格式严格）

一句话总结：JS对象是代码，JSON是数据文本

核心操作：序列化 & 反序列化

前后端交互只有两种操作，全程围绕这两个方法：

  1. 序列化：JS对象 → JSON字符串（上传、传参、存本地） JSON.stringify()
  2. 反序列化：JSON字符串 → JS对象（后端返回数据、解析数据） JSON.parse()

序列化 JSON.stringify()

将 JS 引用类型（对象、数组）转为 JSON 字符串，用于网络传输、本地存储。

反序列化 JSON.parse()

将后端返回的 JSON 字符串，转回 JS 对象，方便代码读取、修改、渲染页面。

JSON 转换专属规则

（后端重点坑点）这部分和 Java 序列化（Jackson）行为几乎一致，联调必懂。

序列化会自动忽略/替换特殊值

  • undefined、函数：直接丢失、被忽略
  • null：正常保留
  • NaN、Infinity：转为 null

只能序列化自有属性

原型链上的属性、方法，序列化时全部丢失，只保留对象自身定义的属性。

不支持循环引用

对象互相引用，序列化直接报错，无法转换。

标准用法（前后端联调固定写法）

场景1：前端传对象参数给后端

后端接口接收 JSON 格式，前端必须先序列化字符串

场景2：后端返回JSON字符串，前端解析使用

结合 BOM 本地存储

localStorage / sessionStorage 只能存字符串，所以对象必须序列化存储，取出必须反序列化。

后端专属对比：JS JSON & Java Jackson

作为后端必须建立对应关系：

  • JSON.stringify等价于 Java objectMapper.writeValueAsString 对象转JSON
  • JSON.parse 等价于 Java objectMapper.readValue JSON转对象
  • JS 丢失 undefined/函数 = Java 忽略 transient、忽略非字段属性

常见报错与排查（联调高频）

报错：JSON.parse() 报错 Unexpected token

99% 原因：

  • 后端返回格式不标准
  • JSON 存在单引号、注释、多余逗号
  • 前端重复 parse（已经是对象还在解析）

小结

  1. JS对象是代码，JSON是纯文本数据，前后端传输只用 JSON；
  2. 序列化 stringify：对象转字符串（传参、存数据）；
  3. 反序列化 parse：字符串转对象（解析后端数据）；
  4. undefined、函数序列化会丢失，NaN、Infinity 会变 null；
  5. 后端联调核心：所有接口对象参数、返回值，底层都是 JSON 转换。

网络请求：AJAX 与 Fetch

前面我们系统学完了 JSON 序列化与反序列化，掌握了前后端数据的转换规则，而网络请求就是前后端数据交互的唯一通道。

对于 Java 后端开发者而言，无需深耕前端请求封装，但是必须彻底弄懂请求流程、参数格式、响应逻辑、跨域原理。日常接口联调、排查报错、解决跨域问题，全部依赖本节知识点。

本文对比原生 AJAX 和现代 Fetch，重点掌握工作主流的 Fetch 请求，吃透 GET、POST 核心用法、请求头、参数传递、响应解析、跨域问题。

网络请求核心概念

前端网络请求，本质是 浏览器主动向后端服务器发送 HTTP 请求，接收后端返回的响应数据，实现页面动态拿数据、提交数据，无需刷新页面。

核心流程统一不变：

前端构造请求 => 发送 HTTP 请求 => 后端接收参数、执行业务逻辑 => 后端返回 JSON 数据 => 前端解析渲染页面

两种核心请求方式

  • GET：查询数据，参数拼接在 URL 地址上，无请求体，参数公开、长度有限制
  • POST：提交数据，参数放在请求体中，私密安全、无长度限制，用于新增、修改、提交表单

前端请求两大方案

  • AJAX（XMLHttpRequest）：原生老旧方案，代码繁琐，兼容所有浏览器，目前基本不再手写
  • Fetch：浏览器现代原生 API，语法简洁、基于 Promise，是当前前端主流原生请求方案

AJAX 原生请求

（了解即可）AJAX 全称异步 JavaScript 和 XML，核心作用是异步请求、局部刷新，是早期前后端交互的核心方案。语法冗余繁琐，仅做原理了解，工作中无需手写。

Fetch 现代网络请求（重点）

Fetch 是浏览器标准化的现代请求 API，基于 Promise 设计，语法简洁、异步逻辑清晰，替代了老旧的 AJAX，是原生前端请求的标准方案，也是前后端联调的核心重点。

Fetch 默认返回 Promise 对象，必须通过 .then 或 async/await 解析数据。

Fetch GET 请求

GET 请求无需配置请求体，参数直接拼接在接口 URL 末尾，适合查询猫咪列表、详情数据。

Fetch POST 请求

POST 用于提交数据，必须手动配置请求方式、请求头、请求体，后端接口绝大多数接收 application/json 格式参数。

请求核心配置详解

请求头 Headers

请求头是前端传给后端的附加信息，后端根据请求头解析参数格式、身份凭证、设备信息，后端开发高频接触。

最核心固定请求头：

  • Content-Type：声明请求体数据格式，常用值 application/json（JSON格式）、application/x-www-form-urlencoded（表单格式）
  • Authorization：身份令牌，用于接口登录鉴权，后端拦截器核心校验参数

请求参数两种格式

URL 参数（GET 专用）

拼接在接口地址后，格式 ?key=value&key2=value2，后端通过请求参数直接获取，无需解析。

Body 请求体（POST 专用）

JSON 格式参数必须序列化，后端通过 @RequestBody 接收，是企业开发主流传参方式。

响应数据解析

Fetch 响应结果是一个 Response 响应对象，不能直接获取数据，两种解析方式：

  • res.json()：解析 JSON 格式响应，返回 JS 对象，99% 接口使用
  • res.text()：解析纯文本响应，用于普通文本、HTML 页面返回

async/await 优雅写法（开发主流）

原生 .then 链式调用嵌套过多会出现回调冗余，搭配 async/await 可让异步请求变成同步写法，代码更简洁，是目前项目标准写法。

跨域问题

后端重中之重，跨域是前后端联调最高频问题，后端必须完全掌握原理和解决方案。

什么是跨域

浏览器同源策略限制：协议、域名、端口号，任意一个不同，即为跨域。

同源策略是浏览器的安全机制，禁止前端跨域名请求后端接口，会直接拦截响应。

跨域产生场景

  • 前端页面：localhost:8080
  • 后端接口：localhost:8090
  • 端口不同，触发跨域拦截，请求失败

后端解决方案（Java 常用）

跨域问题必须后端解决，前端无法根治，Java 后端主流方案：

  • 添加跨域注解 @CrossOrigin
  • 全局跨域配置类配置 CORS
  • 网关统一配置跨域放行

GET 与 POST 核心区别

  • 参数位置：GET 参数在 URL，POST 参数在请求体
  • 安全性：GET 参数公开，不安全；POST 参数隐藏，相对安全
  • 数据长度：GET 有长度限制；POST 无限制
  • 使用场景：GET 查询、POST 新增/修改/提交
  • 缓存：GET 会被浏览器缓存；POST 不会缓存

常见报错与联调排查

  • 跨域报错：后端未配置 CORS，优先检查后端跨域配置
  • 404：接口地址错误、后端接口未部署、请求路径不匹配
  • 405：请求方式不匹配（GET 接口用 POST 请求）
  • 400：参数格式错误、JSON 格式不规范、参数缺失
  • 500：后端代码报错、空指针、事务异常、参数解析异常

小结

  1. 网络请求是前后端数据交互的核心通道，AJAX 老旧淘汰，Fetch 是现代主流原生请求方案；
  2. GET 传参在 URL，用于查询；POST 传参在请求体，用于提交数据，JSON 传参必须序列化；
  3. 请求头 Content-Type 决定参数解析格式，后端 @RequestBody 专属 JSON 格式；
  4. 跨域是浏览器安全限制，由后端统一配置解决，是联调最核心问题；
  5. 生产开发统一使用 async/await 搭配 Fetch，代码简洁易维护。

JS 同步异步与事件循环

前面我们学完了网络请求 Fetch、AJAX 以及定时器，这些代码都有一个共同特征：不会立刻执行、会延后执行。

这就引出了 JS 最核心、最底层的执行机制：同步与异步、宏任务微任务、事件循环。

对于后端开发者来说，不需要手写复杂异步调度，但必须看懂异步代码执行顺序、排查接口时序问题、理解前端为什么不会卡死页面，同时这也是面试高频核心考点。

JS 单线程执行机制

JavaScript 是单线程语言，同一时间只能做一件事。

单线程优势：避免多线程抢占资源、冲突、死锁，适配页面 DOM 操作，防止同时修改同一页面元素引发错乱。

单线程弊端：如果某一段代码耗时过长，会阻塞后面所有代码执行，导致页面卡死、请求卡顿。

为了解决单线程阻塞问题，JS 设计了两套执行模式：同步执行 和 异步执行。

同步执行

同步代码：从上到下逐行执行，上一行执行完毕，才会执行下一行，会阻塞代码流程。

我们之前写的变量定义、循环、判断、对象操作，绝大多数基础代码都是同步代码。

同步代码全部在 执行栈 中执行，执行栈遵循后进先出规则。

执行顺序固定：逐行依次执行，无延迟、无插队、无等待。

异步执行

异步代码：不会阻塞主线程，先跳过延后执行，主线程先跑完同步代码，再回头执行异步代码。

核心作用：解决单线程阻塞问题，实现延时执行、定时任务、网络请求、页面交互。

前端所有异步场景汇总：

  • 定时器：setTimeout、setInterval
  • 网络请求：Fetch、AJAX
  • DOM 事件：click、scroll、input 等事件监听
  • Promise、async/await 异步语法

异步经典案例（必看）

最终输出顺序：

同步代码1 → 同步代码2 → 异步定时器代码

即使定时器延时 0 毫秒，依然优先执行所有同步代码，再执行异步代码，这是 JS 底层固定机制。

任务队列：宏任务与微任务

异步代码不会立刻执行，会根据类型进入不同的任务队列，等待主线程空闲后执行。

JS 将异步任务分为两类：宏任务、微任务。微任务优先级高于宏任务。

宏任务

耗时较长、优先级较低的异步任务，每一轮事件循环只会执行一个宏任务。

常见宏任务：

  • setTimeout、setInterval 定时器
  • AJAX、Fetch 网络请求回调
  • DOM 事件回调
  • 页面渲染、文件读写

微任务

耗时极短、优先级极高的异步任务，一轮循环中，所有微任务会一次性全部执行完，再执行宏任务。

常见微任务：

  • Promise.then、.catch、.finally
  • async/await 后续代码

事件循环执行机制（完整流程）

事件循环是 JS 异步执行的底层逻辑，是浏览器调度同步、异步代码的核心机制，完整执行顺序固定不变。

执行顺序口诀：先同步、后微任务、最后宏任务

完整执行流程：

  1. 主线程优先执行所有同步代码，清空执行栈；
  2. 同步代码执行完毕，主线程空闲，一次性执行所有微任务，清空微任务队列；
  3. 微任务清空后，执行一个宏任务；
  4. 重复上述步骤，循环往复，即为事件循环。

结合猫咪案例，完整还原事件循环执行顺序，吃透底层逻辑。

精准执行顺序解析：

  1. 执行同步代码：打印「同步：初始化猫咪列表」
  2. 遇到定时器宏任务，放入宏任务队列，跳过执行
  3. 遇到 Promise 微任务，放入微任务队列，跳过执行
  4. 执行同步代码：打印「同步：代码执行结束」
  5. 同步代码清空，执行所有微任务：打印「微任务：处理猫咪数据」
  6. 微任务清空，执行宏任务：打印「宏任务：定时器加载猫咪数据」

最终输出顺序：同步初始化 → 同步结束 → 微任务处理数据 → 宏任务定时器加载数据。

后端开发实用价值

作为 Java 后端开发者，无需手写复杂异步调度，但该知识点可以解决绝大多数联调时序问题：

  • 理解为什么网络请求不会阻塞页面渲染
  • 看懂前端接口请求时序错乱、数据未加载完成就渲染的问题
  • 理解 await 为什么可以等待请求结束，实现同步化异步代码
  • 排查定时器延迟、请求回调滞后的底层原因

小结

  1. JS 为单线程语言，通过同步、异步机制解决代码阻塞问题；
  2. 同步代码逐行阻塞执行，异步代码延后非阻塞执行；
  3. 异步任务分为宏任务、微任务，微任务优先级高于宏任务；
  4. 事件循环核心流程：先同步、再微任务、最后宏任务；
  5. 网络请求、定时器、事件监听为宏任务，Promise 回调为微任务。

Promise

上一节我们学完了 JS 事件循环、宏任务与微任务，明确了 Promise 回调属于微任务，优先级高于宏任务。

Promise 是 JS 异步编程的核心语法，彻底解决了传统回调函数的回调地狱问题，也是 async/await 的底层基础。目前所有前端网络请求、异步封装、接口链式调用，全部基于 Promise 实现。

对于后端开发者而言，必须吃透 Promise 状态、链式调用、异常捕获、静态方法，能看懂前端异步接口逻辑、排查请求时序报错、理解前后端异步交互逻辑。

Promise 核心作用

在 Promise 出现之前，JS 异步逻辑全部依赖回调函数嵌套实现。如果存在多层异步依赖（先请求接口A，成功后再请求接口B、C），会出现大量函数嵌套，代码层级混乱、难以维护，这就是回调地狱。

Promise 用链式调用替代嵌套回调，扁平化异步代码，统一异步错误处理机制，让异步逻辑更清晰、可维护、可扩展。

Promise 三种状态

Promise 本质是一个异步任务容器，内部封装异步操作，全程只有三种状态，且状态一旦确定，永久不可更改。

  • pending：初始等待状态，异步任务未执行完成
  • fulfilled：成功状态，异步任务执行成功，返回结果数据
  • rejected：失败状态，异步任务执行失败，返回错误信息

状态流转规则：只能从 pending 转为 fulfilled 或 rejected，不存在反向流转、重复流转。

Promise 基础语法

Promise 是构造函数，通过 new 关键字创建实例，接收一个执行器函数，执行器函数包含两个核心参数：resolve、reject。

  • resolve()：将 Promise 状态改为成功，传递成功结果，触发 .then 回调
  • reject()：将 Promise 状态改为失败，传递错误信息，触发 .catch 回调

Promise 核心方法

then 方法

专门接收 Promise 成功状态的结果，支持链式调用，每次调用都会返回一个全新的 Promise 实例。

核心特性：then 中可以返回普通值或新 Promise，返回值会自动传递给下一层 then。

catch 方法

专门接收 Promise 失败状态的错误信息，同时可以捕获链式调用中任意一层的异常。

开发规范：所有 Promise 异步请求，必须搭配 catch 捕获异常，避免前端报错卡死。

finally 方法

无论 Promise 最终成功还是失败，一定会执行的回调，常用于关闭加载状态、结束请求加载动画、清空临时数据。

Promise 链式调用（解决回调地狱）

实际开发中经常存在异步串行场景：查询猫咪列表 => 根据猫咪ID查询详情 => 根据详情查询饲养记录。

传统回调会多层嵌套，代码臃肿；Promise 链式调用从上到下平铺执行，逻辑清晰。

Promise 静态方法（开发高频）

Promise 内置四个核心静态方法，用于批量处理多个异步请求，是前后端联调高频用法。

Promise.all

接收 Promise 数组，所有请求全部成功，整体才成功，返回结果数组；任意一个请求失败，整体直接失败。

适用场景：多个互不依赖的接口，需要全部加载完成再渲染页面。

Promise.race

接收 Promise 数组，谁先完成就返回谁的结果，无论成功失败，其余请求继续执行但结果被忽略。

适用场景：接口请求超时拦截、最快响应优先展示。

Promise.allSettled

接收 Promise 数组，等待所有请求执行完毕，无论成功失败，统一返回所有结果状态。

适用场景：批量操作（批量新增、批量删除），需要统计成功数量和失败数量，不因为个别失败中断整体流程。

Promise.resolve / Promise.reject

快速创建成功/失败的 Promise 实例，常用于代码兼容、统一返回格式。

Promise 与事件循环关联复盘

结合上一节事件循环知识点，明确执行优先级：

Promise 的 .then / .catch / .finally 属于微任务，定时器、网络请求回调属于宏任务。

执行顺序：同步代码 > Promise微任务 > 宏任务，这也是 Promise 异步优先级更高的底层原因。

后端开发核心关注点

  • 看懂前端接口链式请求逻辑，理解前端异步串行、并行请求方式
  • 排查前端接口报错、异常捕获失效、请求时序错乱问题
  • 理解 Promise.all 批量请求场景，对应后端批量接口设计
  • 为后续 async/await 语法打基础，async/await 是 Promise 语法糖

小结

  1. Promise 三种状态：pending、fulfilled、rejected，状态一旦锁定不可修改；
  2. resolve 触发成功回调 then，reject 触发失败回调 catch，finally 无论结果必执行；
  3. 链式调用彻底解决回调地狱，扁平化多层异步逻辑；
  4. all 全部成功、race 竞速执行、allSettled 全部完成，适配不同批量请求场景；
  5. Promise 回调属于微任务，优先级高于宏任务，是 JS 异步核心底层语法。

async / await 与 try-catch 异常捕获

上一节我们完整掌握了 Promise 的底层机制、链式调用、静态方法，解决了回调地狱问题。但 Promise 链式调用依旧存在多层链式嵌套，代码可读性仍有优化空间。

async/await 是 ES8 推出的 Promise 语法糖，它并不会改变 Promise 底层原理，只是将异步代码模拟成同步写法，让异步逻辑自上而下平铺执行，是目前前端项目、接口请求的主流标准写法。

搭配 try-catch 可以优雅捕获所有异步异常，彻底统一前端异步代码的书写规范，也是前后端联调必懂核心语法。

async / await 核心作用

单纯的 Promise 链式调用，多层异步依赖依旧会出现链式堆叠，阅读体验差。async/await 的核心价值，就是抹平异步代码层级，用同步写法执行异步操作。

底层本质：依然基于 Promise + 事件循环微任务机制实现，只是语法层面做了简化封装。

所有的 async/await 代码，都可以百分百还原为 Promise 写法，反之不成立。

async 函数基础规则

async 用于修饰函数，写在函数定义最前方，被修饰的函数具备两个核心特性。

  • 函数内部可以使用 await 关键字，普通函数禁止使用
  • 函数的返回值永远是 Promise 实例，即使手动返回普通数据，也会自动包装为成功状态的 Promise

await 核心规则

await 是等待关键字，是整个语法的核心，专门用于等待 Promise 执行完成。

核心逻辑：暂停当前代码执行，直到 Promise 状态变更，再向下执行，完美模拟同步执行时序。

严格使用限制：只能在 async 函数内部使用，全局、普通函数中直接报错。

异步串行依赖（核心场景）

工作中最常用的场景：多个接口存在先后依赖，必须 A 接口执行完成，再执行 B 接口、C 接口。

Promise 需要多层链式嵌套，async/await 直接自上而下平铺书写，可读性拉满。

try-catch 异常捕获

async/await 彻底舍弃了 .catch 链式捕获方式，统一使用try-catch 捕获异步异常，是官方标准规范。

核心原理：await 等待的 Promise 如果进入 rejected 失败状态，会直接抛出异常，终止代码执行，必须通过 catch 捕获拦截。

语法结构

  • try：包裹正常异步业务代码，执行正常逻辑
  • catch：捕获 try 代码块中所有异常，防止页面报错卡死
  • finally：可选，无论成功失败都会执行，用于收尾操作

优势：一次捕获，覆盖当前函数所有异步报错，无需每一层接口单独写异常回调，代码极简。

异步并行执行优化

await 默认串行执行，多个无依赖接口会依次等待，造成耗时叠加、请求变慢。

无依赖的并行请求，搭配 Promise.all 实现高效并发，是项目高频优化写法。

串行总耗时：1000ms + 500ms = 1500ms；并行总耗时：最大耗时 1000ms，大幅提升请求效率。

核心执行机制复盘

结合之前事件循环、Promise 知识点，彻底理清底层逻辑：

await 并不是阻塞浏览器，只是阻塞当前 async 函数内部代码，主线程同步代码、其他异步任务正常执行。

await 等待的 Promise 回调，依旧属于微任务，遵循事件循环执行优先级。

后端开发核心关注点

  • 看懂前端主流接口请求写法，99% 现代项目接口请求均为 async/await + try-catch
  • 理解前端异步串行、并行请求逻辑，对应设计后端接口并发、批量查询方案
  • 排查前端报错、接口超时、参数解析异常，看懂前端异常捕获逻辑
  • 区分串行与并行请求耗时差异，优化前后端联调接口性能

小结

  1. async/await 是 Promise 语法糖，底层不改变异步机制，仅优化代码写法；
  2. async 修饰函数返回 Promise，await 只能在 async 函数内使用，用于等待异步结果；
  3. 异步串行依赖优先使用 await，无依赖并行请求搭配 Promise.all 优化性能；
  4. 统一使用 try-catch 捕获异步异常，替代链式 catch，代码更简洁规范；
  5. 是目前前端网络请求、异步业务的最终标准化写法。

ES6+ 高频语法精选

let / const 变量声明

作用域、var/let/const、变量提升、暂时性死区 TDZ

作用域是 JS 变量的生效范围，是读懂代码变量冲突、赋值异常、未定义报错的底层核心。ES6 之后 let/const 彻底重构了 JS 作用域规则，完全区别于老旧 var。对于后端开发者，掌握本节内容可以快速排查前端变量污染、重复声明、取值异常、逻辑错乱等常见问题。

作用域分类

JS 作用域分为三类，对应变量不同的生效范围，层级由外到内逐层嵌套。

全局作用域

脚本全局区域，所有代码都能访问，页面加载全程生效。挂载在全局的变量，整个页面任意函数、逻辑中都可以直接读取使用。

函数作用域

仅在函数内部生效，函数执行结束后，内部变量自动销毁，外部无法访问。var 声明的变量仅支持全局作用域和函数作用域。

块级作用域

ES6 新增作用域，由 {} 包裹形成，if、for、while、代码块都能生成独立作用域，仅 let、const 支持块级作用域，var 不支持。块级作用域彻底解决了全局变量污染问题。

var / let / const 核心差异对比

三者是 JS 变量声明的全部方式，差异集中在作用域、变量提升、重复声明、赋值规则，是读代码、排报错的基础。

var 老旧声明方式

  • 无块级作用域，只有全局、函数作用域
  • 存在变量提升
  • 允许重复声明同名变量，不会报错，容易覆盖数据
  • 可重复赋值，初始值为 undefined

let 可变变量声明

  • 支持块级作用域
  • 无变量提升，存在暂时性死区
  • 禁止重复声明同名变量
  • 支持二次赋值，适用于会变更的变量

const 常量声明

  • 支持块级作用域
  • 无变量提升，存在暂时性死区
  • 禁止重复声明
  • 声明必须初始化，不允许二次赋值
  • 引用类型常量可修改内部属性，仅禁止地址修改

变量提升

变量提升是 JS 老旧机制，仅 var 存在变量提升，let/const 不存在变量提升。

变量提升规则：JS 代码执行前，会预先扫描所有 var 声明的变量，将变量声明提升到当前作用域最顶部，赋值保留在原位置。提升后变量默认值为 undefined，会出现先使用、后声明的诡异现象。

变量提升会导致代码逻辑混乱、隐性 bug，这也是现代开发彻底废弃 var 的核心原因。

暂时性死区 TDZ

TDZ 是 let/const 特有的机制，全称暂时性死区。在当前块级作用域内，变量声明之前的区域，属于该变量的死区，死区内禁止访问变量，访问直接报错。

let/const 虽然不会变量提升，但代码执行前依然会绑定当前块级作用域，提前锁定变量，杜绝变量污染和错乱访问。

暂时性死区的核心价值：杜绝变量污染、避免作用域错乱、强制变量先声明后使用，让代码更严谨、可预测。

作用域链查找规则

当当前作用域读取变量时，自身没有该变量，则向外层嵌套作用域逐级查找，直到全局作用域，找不到则报未定义错误，这就是作用域链。

实用总结

  • 永远不用 var，全部使用 let/const，规避变量提升、全局污染问题
  • const 优先，仅变量需要重新赋值时用 let，符合现代编码规范
  • 块级作用域隔离变量，避免接口请求、循环逻辑的变量互相干扰
  • 暂时性死区杜绝变量提前访问报错，快速定位前端代码语法问题
  • 作用域链理解变量取值规则，排查前端数据取值错乱、覆盖异常

本节小结

  1. 作用域分为全局、函数、块级，let/const 支持块级作用域，var 不支持；
  2. var 存在变量提升、允许重复声明、易污染全局，现代项目彻底废弃；
  3. let/const 存在暂时性死区，必须先声明后使用，代码更严谨；
  4. const 禁止重赋值，但允许修改引用类型内部数据；
  5. 变量查找遵循作用域链，由内向外逐级查找。

this 完整规则

this 是 JS 中最容易混淆的知识点，它不是固定值，函数的调用方式决定了 this 的指向，和函数定义位置无关。

对于后端开发者，不需要手写复杂 this 绑定，但必须看懂各类场景下的 this 指向，排查前端取值 undefined、对象属性拿不到、回调赋值错乱等高频 bug。

本文统一梳理 普通函数、对象方法、定时器、回调函数、箭头函数 五大核心场景，全网最精简、最实用判断规则。

普通函数调用

纯粹的独立普通函数直接调用，this 默认指向 全局对象 window，在严格模式下指向 undefined。

核心口诀：谁都不归属，默认指向全局。

严格模式下，可以避免 this 胡乱指向全局，规避隐性变量污染问题。

对象方法调用

函数作为对象的属性方法被调用时，this 指向 调用该方法的对象。

核心口诀：谁调用，this 就是谁，是工作中最常用、最好理解的规则。

注意：方法必须通过 对象.方法() 调用，才会绑定当前对象。

定时器回调

setTimeout、setInterval 定时器内部的普通函数，this 固定指向 window。

原因：定时器回调是浏览器全局异步调用，不属于任何对象，遵循普通函数全局绑定规则。

这是经典报错场景：对象内部定时器拿不到自身属性，常规解决方案是提前保存外层 this。

普通回调函数

数组高阶方法、事件回调、接口回调中的 普通函数，this 默认指向 window。

回调函数本质是“被别人调用”的独立函数，失去外层对象绑定，this 回归全局。

箭头函数专属规则（重点）

箭头函数 没有自己的 this，也不遵循上面任何调用规则。

箭头函数的 this 指向 定义位置的外层作用域 this，永远固定，不会被调用方式改变。

核心口诀：箭头函数看定义，不看调用。

  • 定时器普通回调 = window
  • 数组遍历普通回调 = window
  • 箭头函数 = 继承外层作用域this，固定不变

实用价值

  • 看懂前端定时器、接口回调、遍历回调中undefined 报错根源
  • 理解前端为什么用箭头函数锁上下文、为什么保存 _this
  • 排查前端异步赋值失效、对象属性读取失败的常规问题
  • 读懂现代项目全箭头函数写法的底层逻辑

本节小结

  1. 普通函数、定时器回调、遍历回调，无归属调用时 this 指向 window；
  2. 对象方法调用，this 指向调用者，遵循谁调用指向谁；
  3. 箭头函数无独立 this，继承定义时外层作用域上下文；
  4. 箭头函数是解决异步回调 this 错乱的最优方案，是项目主流写法。
