自娱自乐的XSS

发表于2026-09-01|更新于2026-09-02
|总字数:6342|阅读时长:26 分钟|浏览量:

为什么说陌生的链接不要点？哪怕域名看起来正常也不要乱点，接下来告诉你为什么。提醒一下：未经授权，禁止对任何互联网网站、系统开展漏洞探测、渗透测试、XSS 等攻击实验。一切未取得书面授权的攻击行为，违反《网络安全法》，需承担相应民事、行政乃至刑事责任。本内容仅用于安全学习与原理研究。

XSS (Cross Site Scripting) 即跨站脚本攻击，为了不与层叠样式表 (Cascading Style Sheets, CSS) 的缩写混淆，故将跨站脚本攻击缩写为 XSS。为什么我说这是自娱自乐呢？因为就我之前的学习，里面有一个能实现的攻击方式条件十分苛刻，而且挺容易翻车，自己自娱自乐玩玩得了。现在再来详细总结一下。

听说有兄弟面试后端开发被面试官找茬问了个这个前端的漏洞，没想到连听都没听说过，啥玩意儿是叉艾斯艾斯啊？但是跨站脚本攻击（XSS）作为Web安全领域中最常见、危害最广泛的漏洞之一，长期位列OWASP Top 10榜单，作为开发人员也还是有必要了解一下的。

前置知识

XSS一途如逆水行舟，若各位道友提前觉醒了些许前端姿势：HTML标签/事件、JSDOM操作、同源策略、浏览器解析机制、URL组成等，境界根基扎实，则修为一日千里，前途不可限量！

W3C

万维网联盟（World Wide Web Consortium）制定 Web 国际标准的中立组织，非营利联盟，目标：统一网页规范，让网页在不同浏览器上表现一致（One Web）
浏览器、HTML、DOM、CSS 等的规则，由 W3C 定义标准文档，Chrome/Edge/Firefox 按照标准去实现

DOM

文档对象模型（Document Object Model），W3C 标准，页面加载后浏览器解析 HTML，把 HTML 文档解析成一棵节点树（DOM 树），JS 可以读取、修改、删除页面上 HTML 标签 / 文本。树上每一个标签、文本、注释都是**DOM 节点 (Node)**。

所以DOM既是这个节点树模型，也是一套用来操作该模型的 API 接口集合（DOM 模型& DOM API）。W3C 定义了这套接口规范，让 JS 可以读写、修改删除HTML 标签与文本。DOM 的入口对象是document(window.document)，为整个 HTML 文档入口，用法：

  • 查找全局节点、创建新节点的 API，需要 document.xxx，例如 getElementById、querySelector、createElement；
  • 拿到元素节点对象之后，可以直接 元素.xxx，如修改内容 innerHTML / textContent，增删节点 appendChild()、remove()。

BOM

浏览器对象模型（Browser Object Model），是JavaScript与浏览器交互的接口。location、navigator、history都是挂载在window下的 BOM 子对象。window是浏览器的全局顶层对象，本身属于 BOM；DOM 入口对象也document挂载在window下，但 document不属于BOM。

若无同名局部变量，代码中的window.一般可以省略。

window（BOM顶层对象、浏览器全局对象）
├─ location（BOM）
├─ navigator（BOM）
├─ history（BOM）
└─ document（挂载在window下，但属于DOM体系，不属于BOM）

PS： document是 DOM 对象；document.xxx的xxx 是这个对象的方法 / 属性，属于 DOM API；
location 是 BOM 对象；location.xxxx的xxxx，是这个对象的属性 / 方法，属于 BOM API。

例如：window.document可直接操作 DOM，location.hostname能获取域名信息。当攻击者能在页面中插入并执行包含BOM操作的JavaScript代码时，XSS漏洞便可能被触发——这正是XSS的本质：恶意脚本在用户浏览器中被执行。

Cookie

一、什么是 Cookie？

HTTP Cookie（简称 Cookie）：服务端下发给浏览器，浏览器本地保存的一小段文本数据。 HTTP 协议本身是无状态的，服务器无法识别两次请求是不是同一个用户；Cookie 就是用来保存状态，让服务器识别用户。

二、完整工作流程（3 步）

1、用户登录，服务器返回 HTTP 响应头：Set-Cookie，下发 Cookie 给浏览器

HTTP/1.1 200 OK
Set-Cookie: PHPSESSID=abcd123; Path=/; Domain=test.com; Max-Age=3600; HttpOnly; Secure

2、浏览器收到，按域名、路径、有效期把 Cookie 保存在本地。

3、浏览器再次访问匹配域名路径，自动在请求头带上Cookie字段发给服务器：

GET /index HTTP/1.1
Cookie: PHPSESSID=abcd123

服务器读取 Cookie，判定用户身份，维持登录状态。

三、Cookie 两大分类

1、会话 Cookie（Session Cookie）：不设置Expires/Max-Age。关闭浏览器自动删除； 用途：临时登录会话。
2、持久 Cookie：设置Expires（绝对时间）/Max-Age（相对秒数）； 浏览器保存到硬盘，到期自动删除，关闭浏览器依然存在。

四、Cookie 属性（XSS、CSRF ）

1、Name=Value：Cookie 核心键值，比如PHPSESSID=xxx

2、Domain：生效域名

  • Domain=test.com：test.com以及所有子域名xxx.test.com都可以携带这个 Cookie
  • 不写 Domain，默认当前域名，子域名无法共享

3、Path：URL 路径匹配

  • Path=/：网站全部页面生效
  • Path=/admin：仅访问/admin及其子路径才携带 Cookie

4、Max-Age / Expires：有效期

  • Max-Age=3600：3600 秒（1 小时）
  • Expires：指定一个 GMT 时间

5、Secure：Cookie仅在 HTTPS 加密请求中携带；HTTP 明文请求不会发送 Cookie。 作用：防中间人抓包窃取 Cookie。

注意：Secure 不阻止 JS 读取 Cookie（HttpOnly 才管 JS 读取）

6、HttpOnly 禁止 JS 使用 document.cookie 读取这个 Cookie， 但是浏览器发 HTTP 请求的时候依然自动带上 Cookie ，作用：减轻 XSS 的危害；XSS 无法拿到 Cookie 字符串，但依旧可以 AJAX 发包执行操作

7、SameSite（防御 CSRF 核心属性，3 个值）

  • SameSite=Strict：完全禁止跨站请求携带 Cookie。跨站 GET/POST 都不带 Cookie，CSRF 防御最强
  • SameSite=Lax（现代浏览器默认）：跨站GET 点击链接允许携带 Cookie；跨站 POST 表单不携带 Cookie
  • SameSite=None：允许跨站携带 Cookie；必须同时带上 Secure，否则无效

五、Cookie 常见用途

1、会话维持（登录凭证 sessionid，最核心）
2、用户偏好：语言、深色模式
3、购物车
4、用户行为统计、广告追踪

六、JS 操作 Cookie

七、Cookie 相关安全漏洞（结合前面 XSS、CSRF）

1、XSS：拿到非 HttpOnly Cookie，会话劫持；HttpOnly 可以阻止读取 Cookie，但无法阻止 AJAX 发包
2、CSRF：利用浏览器自动携带 Cookie，跨站发起请求冒充用户操作；SameSite用来防御 CSRF
3、中间人劫持 MITM：HTTP 明文传输，抓包拿到 Cookie；Secure 属性解决
4、Cookie 注入、CRLF 注入：伪造 Set-Cookie 头植入 Cookie

XSS基础

介绍

跨站脚本攻击，为何称为“跨站”攻击？攻击者并非直接攻击用户主机，而是通过第三方可信网站（存在XSS漏洞的站点）作为跳板：恶意脚本从漏洞站点加载，却能窃取用户与该站点的会话数据（如Cookie），或冒充用户执行操作，形成“跨站”攻击链路。

触发条件

1、用户可控制某个输入参数（如搜索框、URL参数）；
2、后端未对输入进行转移或过滤；
3、输入内容被页面输出展示。

危害

  • 窃取cookie、token、session等身份凭证来获得用户登录态劫持账户；
  • 获取客户端信息（浏览器版本、操作系统、地理位置）
  • 劫持流量，把用户正在访问的页面跳转到钓鱼网站；
  • 盗用账户来转账、群发信息等；
  • 记录用户键盘操作，窃取敏感信息（密码、手机号）；
  • 利用用户的设备来发起DDOS攻击；
  • 结合其他漏洞（如CSRF）实现远程代码执行，甚至控制服务器。
  • 其它骚操作。。

如何寻找？

手动测试：“见框就插”，对所有输入点（表单、URL参数、HTTP头）尝试注入测试脚本（如<script>alert(15464274624532546357572)</script>）；
自动化工具：使用Xray、AWVS、XSStrike等工具扫描，或Burp Suite插件辅助检测；
复杂场景：需结合业务逻辑手动绕过过滤规则（如编码变形、事件触发）。

XSS分类

根据恶意脚本的存储方式和执行流程，XSS可分为三类，其核心差异如下表所示：

反射型 恶意脚本经服务器“反射”后执行，不存储在服务器，仅单次请求有效 URL参数、HTTP请求头 诱导用户点击含恶意脚本的URL 低危（我感觉利用好了都是高危）

XSS利用方式

Cookie的获取

HttpOnly 前提：

在XSS这种攻击中，cookie 值由使用 JavaScript ( document.cookie) 的客户端脚本访问。然而，在日常使用中，Web 应用程序很少需要通过 JavaScript 访问 cookie。因此，设计了一种保护 cookie 免受此类盗窃的方法：一个标志，告诉 Web 浏览器 cookie 只能通过 HTTP 访问 - HttpOnly标志。

三者能不能读到 Cookie、读取条件，唯一影响因素便是 HttpOnly 属性，如果 Cookie 设置了 HttpOnly = true，那么document.cookie便无法读取 Cookie。后面会提供一个绕过思路。

?query （查询字符串 /query 参数）

基础绕过：

绕过htmlspecialchars():

htmlspecialchars() 默认转义这 5 个字符： & < > " '。

核心原理：其只能防御【HTML 上下文】注入； 如果你的注入点在 html 标签属性值 / javascript 上下文 / href、src 这类属性，存在绕过机会。并且此函数默认配置不会过滤单引号，设置了quotestyle 规定如何编码单双引号才能过滤单引号

HttpOnly绕过：

HttpOnly 是 Cookie 的属性，作用是：浏览器禁止document.cookie读取这个 Cookie。浏览器标准规范（RFC 标准），现代浏览器（Chrome、Firefox、Edge、Safari）全部遵守这个规范。幻想找一个老旧浏览器，不识别 HttpOnly 字段，JS 就能读到 HttpOnly Cookie 一般是不现实的。

利用思路：

HttpOnly 阻止 JS 读取 Cookie 字符串，但不会阻止同源 AJAX 请求自动携带 Cookie；XSS 可以直接调用接口执行业务操作，但是拿不到 Cookie 明文；没有通用、稳定的 HttpOnly 绕过方法。

XSS 存在时，在目标站点同源环境，可以直接发起 AJAX/Fetch 请求，浏览器自动带上 HttpOnly Cookie，直接执行业务操作。示例：

能力：改密码、发帖、读取页面接口返回数据；缺点：拿不到明文 Cookie 字符串。

其它漏洞：

真正能拿到 HttpOnly Cookie 的场景（条件苛刻）：

1、中间人攻击 MITM（HTTP 协议）流量明文传输，抓包获取请求里的 Cookie。HTTPS 环境无效。
2、存在响应头漏洞 / 网页返回 Set-Cookie 且页面可控制 极少情况，页面把 Set-Cookie 内容输出到响应体，可读取。
3、客户端本地漏洞 浏览器漏洞、恶意插件，读取本地 Cookie 文件（属于浏览器底层漏洞，不是 Web XSS 层面绕过）。

XSS的修复

XSS 本质：把用户可控输入当成代码 / 标签解析执行，修复思路就是让浏览器把用户输入当成普通文本，不解析 HTML、JS。

一、不同上下文的修复方案

  1. HTML 正文上下文（标签之间，这里）

    使用 HTML 转义：转义

    • PHP：htmlspecialchars($str, ENT_QUOTES) 一定要带上ENT_QUOTES，单引号也转义
    • JS 前端：textContent（推荐，直接纯文本渲染，不会解析 HTML）

  2. HTML 属性上下文（``）

    • 转义：& < > " '
    • 额外：属性值必须用引号包裹，不要写无引号属性，防止闭合逃逸

  3. JavaScript 上下文（var a="可控输入"），HTML 转义不够，需要 JS 转义：转义 \ " ' / \n，或者 JSON 序列化，推荐不要直接把变量插入 script 标签，尽量把数据放在data-*属性，JS 读取

  4. URL 上下文（href、src）

    • 先校验协议：只允许 http:// https://，禁止 javascript:伪协议
    • 使用 url 编码 encodeURI()

二、前端修复

DOM-XSS 专属，DOM-XSS 后端拿不到 payload，后端过滤无效，DOM-XSS 漏洞根源：前端 JS 直接用innerHTML、document.write、eval()、setTimeout("字符串")等函数拼接可控输入。安全写法：

  • 优先 textContent，代替 innerHTML
  • 禁止直接将 URL hash /search 的用户输入送入innerHTML、eval、危险 API：innerHTML、outerHTML、document.write、eval、new Function、setTimeout(字符串)

三、CSP

CSP 是 HTTP 响应头content security policy，采用白名单机制，告诉浏览器：哪些来源的资源允许加载、哪些 JS 允许执行；兜底防御，即使代码不小心漏了过滤，CSP 可以阻止未授权 JS 执行，就算页面存在注入点，恶意 JS 也跑不起来。属于第二层防护，响应头示例：

含义：只允许加载本站资源，禁止内联 JS、javascript:伪协议，阻断 XSS 执行。

局限：
1、CSP 不能修复代码漏洞，只是缓解：代码注入漏洞依旧存在，只是恶意 JS 无法执行
2、如果配置写了 'unsafe-inline' / 'unsafe-eval'，防护直接失效，XSS 依然能触发
3、DOM-XSS 如果是允许的外部 JS 源内执行，CSP 拦不住
4、不能防御 CSRF，不能防点击劫持（点击劫持是 X-Frame-Options）

四、Cookie 安全加固

降低 XSS 成功后的危害，不能阻止 XSS 触发

  • HttpOnly：禁止document.cookie读取 Cookie，防止 Cookie 窃取
  • Secure：仅 HTTPS 传输 Cookie

注意：HttpOnly不能阻止 XSS 本身，XSS 依旧可以 AJAX 自动携带 Cookie 执行业务操作

五、输入过滤

黑名单（过滤``、alert）：容易被各种绕过（大小写、双写、svg 等），不安全；白名单：只允许合法字符，比如用户名仅允许中英文、数字。黑名单不推荐，优先白名单

XSS与CSRF的区别：

XSS 是在目标站点同源执行 JS，可读取页面数据 / 偷 Cookie；CSRF 是诱导浏览器跨站自动带 Cookie 发包，只能代用户执行业务操作，不能读取目标页面内容。CSFR之后再更新文章具体讲述。
