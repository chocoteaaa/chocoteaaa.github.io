CSRF给我打钱！

发表于2026-09-06|更新于2026-09-06
|总字数:12286|阅读时长:49 分钟|浏览量:

当你登录到自己的账号上时，突然跳出一个神秘小窗口通知假期延长，你如果控制不住好奇点进去，那么你惊奇的发现你的钱被转走了，这说明存放你账户的网站可能存在 CSRF 漏洞，并且没有防护。

本来仅仅想总结一下之前学的内容，结果与时俱进了一下没想到这么多。之前觉得 CSRF 跟 XSS 有些地方挺像的，但其实 XSS 属于前端相关漏洞，但 CSRF 本质不是前端漏洞，是服务端验证逻辑漏洞，只是利用时依赖前端页面发起请求。

而且我之前感觉 CSRF 是一个很老套的漏洞，没啥含量，就写一个页面构造 payload ，实现条件苛刻（必须诱导用户访问恶意页面、用户必须处于登录状态、只能发起请求，无法读取后端响应内容、受浏览器安全策略限制、攻击载荷固定，无法动态获取一次性凭证、部分请求无法构造）还容易被溯源、特征明显，但是今天一总结才发现现代 CSRF 的攻击面、利用方式比我想象的要广，这一点从文末纵深防御，总结及现状也能看出来。

前置知识

在OWASP Top 10中，从 2017 版开始，CSRF 被移出 OWASP Top 10 主列表，这并非因为和我想的一样 CSRF 太弱了，而是 OWASP 认为随着现代框架（如 Rails、Django、Spring）内置 Token 防护、以及 SameSite Cookie 的普及，其整体风险排名被其他更普遍的漏洞（如 SSRF、不安全的反序列化）超越。它从”独立的大漏洞”演变为”分散在访问控制、认证失败中的持续威胁”，在 API 安全、内网渗透、供应链攻击中依然活跃。

介绍

CSRF 全称：Cross‑Site Request Forgery，跨站请求伪造。和XSS一样称为跨站，只不过XSS是脚本攻击而CSRF是请求伪造，转走你账户的钱便是伪造转账请求的操作。XSS 是在目标站点同源执行 JS，可读取页面数据偷 Cookie；CSRF 是诱导浏览器跨站自动带 Cookie 发包，伪装用户执行业务操作，一般不能读取目标页面内容。

CSRF 漏洞的核心本质：利用浏览器跨站请求时自动携带 Cookie的特性。攻击者构造恶意页面，欺骗处于登录状态的用户浏览器，在用户不知情的情况下向已登录的目标网站发起请求，自动执行操作（发消息、改资料、扣款等）。因浏览器请求自带用户会话 Cookie，服务端误认为该请求是用户本人发起的合法操作并执行。
漏洞根源：服务端只依赖 Cookie 做身份认证，没有校验这个请求是不是用户主动发起。

一、前提条件

1、A 网站（资金网站）存在 CSRF 漏洞：鉴权只依赖 Cookie，没有 CSRF Token、没有校验 Origin/Referer，Cookie 的 SameSite 未开启。

2、用户已经登录 A 网站，浏览器保存了 A 网站的登录 Cookie。

3、攻击者提前搭建恶意网站 B。

4、攻击者需精准构造与目标操作完全一致的请求（包括 URL、请求方法、参数、HTTP 头），重要操作的所有参数都是可以被攻击者猜测到的，如 “修改密码” 的请求为：

Cookie: session=abc123…（用户已登录的会话 Cookie）

5、用户在认证状态下访问恶意页面（如点击钓鱼链接、浏览含恶意代码的网页），触发恶意请求。此时浏览器会自动携带目标网站的 Cookie，服务器无法区分请求是用户主动发起还是恶意伪造。

CSRF 攻击方式详解

除了 GET 和 POST，CSRF 的攻击面远比我想象的要广

从攻击载体维度，CSRF 可分为无脚本型、脚本型、组合型与存储型四大类。无脚本型依赖浏览器解析 HTML/CSS 标签时的自动请求行为，隐蔽且不受 CORS 限制；脚本型依赖 JavaScript 的主动编程能力，灵活强大但受同源策略约束；组合型通过与 Clickjacking 或 XSS 联动，突破现代防御体系；存储型则是一种持久化投递渠道，其植入的 Payload 可触发前三类中的任意攻击。

基础的利用方式学习下面的部分只看GET和POST部分就行，看完就可以不看了，剩下的之后再处理，现在很多工具都能自动生成 payload。

〇、前置知识

1、俩请求

简单请求（Simple Request）和非简单请求（Preflighted Request）是 CORS（跨域资源共享）机制中的核心概念，直接决定了跨域请求能否直接发送到服务端。

简单请求

浏览器不会先发 OPTIONS 预检，而是直接发送实际请求。服务端收到请求并处理动作后，浏览器再检查响应中的 CORS 头，决定是否允许前端读取响应。

非简单请求

浏览器必须先发送一个 OPTIONS 预检请求，询问服务端”我接下来要发的这个请求，你允许吗？”。只有服务端明确放行，浏览器才会发送真正的请求。

对 CSRF 的核心影响：简单请求 = 服务端动作一定会执行（无论 CORS 是否允许读取响应）；非简单请求 = 如果预检不通过，实际请求根本发不出去，攻击失败。

2、简单请求判定标准

必须同时满足以下三个条件，缺一不可：

条件 1：请求方法只能是以下之一

  • GET
  • HEAD
  • POST

条件 2：请求头只能包含以下字段

  • Accept/Accept-Language/Content-Language/Content-Type（但值必须满足条件 3）/DPR/Downlink/Save-Data/Viewport-Width/Width/Last-Event-ID

注意：如果添加了任何自定义头（如 X-CSRF-Token、Authorization、X-Requested-With），立即变为非简单请求。

条件 3：Content-Type 只能是以下之一

  • application/x-www-form-urlencoded
  • multipart/form-data
  • text/plain

注意：application/json 不在此列！这意味着用 fetch() 发送 JSON 数据必然触发预检。

三、非简单请求的特征

只要违反上述任意一条，即为非简单请求：

触发条件 示例
方法不是 GET/HEAD/POST PUT、DELETE、PATCH、OPTIONS
包含自定义请求头 X-CSRF-Token: abc123
Content-Type 为其他值 application/json、application/xml
请求使用了 ReadableStream fetch() 的 body 为流对象

四、在 CSRF 中的意义

1、为什么 HTML Form 是 CSRF 的”黄金标准”？

HTML Form 提交时：

  • 方法：GET 或 POST
  • Content-Type：application/x-www-form-urlencoded 或 multipart/form-data
  • 无自定义 Header

天然满足简单请求三要素，因此：

  • 不触发 OPTIONS 预检
  • 请求直接到达服务端
  • 服务端一定执行动作
  • CORS 完全无法阻止攻击

3、自定义头的”双刃剑”

开发者可能认为”加了自定义头就安全”：

真相：

  • 从防御角度：确实触发了非简单请求，增加了 CSRF 难度
  • 从攻击角度：如果目标 CORS 配置错误（允许攻击者域名），攻击者同样可以用 JS 设置该 Header，防御失效
  • 更安全的做法：使用 X-CSRF-Token 并确保 Token 与会话绑定

CORS 与 CSRF 的核心关系

CORS 阻止的是跨域”读取响应”，不是”发送请求”。 对于简单请求，无论 CORS 是否允许，请求都会到达服务端并执行动作。因此 CORS 不是 CSRF 的防御机制。

一、无脚本型 CSRF（No-Script）

不依赖 JavaScript，仅利用浏览器解析 HTML/CSS 标签时的自动请求行为。

1、GET 自动加载型

① Img 标签（最经典）

原理：浏览器解析 HTML 时，遇到 <img> 标签会立即发起 GET 请求加载图片资源。该请求由浏览器内核自动调度，无需用户交互，且会自动携带目标域的 Cookie（受 SameSite 策略限制）。同源策略（SOP）限制的是跨域读取响应内容，不限制跨域发送请求，因此即使无法获取图片内容，请求本身已到达服务端并执行动作。

适用场景/作用：

  • 目标将敏感操作误用为 GET 方法（如 /delete?id=1、/logout、/changeEmail?email=xxx）
  • 目标 Cookie 设置为 SameSite=None 或未设置 SameSite（老旧浏览器）
  • 同站攻击（子域到主域）时不受跨站限制
  • 配合日志/分析系统实现”盲打”（如通过请求记录确认用户访问了恶意页面）
  • 页面渲染即触发，用户无感知
  • 只能攻击 GET 接口

② Iframe 隐藏框架

原理：<iframe>加载页面时，浏览器会发起 GET 请求获取目标页面内容。与 <img> 类似，该请求自动携带 Cookie，且<iframe>可通过style="display:none"完全隐藏。

适用场景/作用：

  • 目标对 <img> 标签做了过滤或拦截（如 WAF 检测图片后缀）
  • 需要加载完整页面而非单一资源（如触发页面内嵌的 JavaScript 执行）
  • 某些场景下 iframe 的加载优先级与 img 不同，可作为替代方案

③ CSS 属性驱动

原理：浏览器解析 CSS 时，遇到 url() 函数会发起 GET 请求加载外部资源。这包括 background-image、@import、@font-face 等属性。其本质与 `` 完全相同，都是浏览器自动发起的子资源请求。

适用场景/作用：

  • 目标对 HTML 标签做了严格过滤，但未对 CSS 内容做校验（如允许用户自定义主题、昵称样式）
  • 更加隐蔽：CSS 加载失败不会在页面上留下”裂图”痕迹
  • 适用于通过富文本编辑器注入样式攻击的场景

④ Link Prefetch（稳定性差，仅了解）

原理：<link rel="prefetch"> 是浏览器提供的资源预加载机制，浏览器可能在空闲时自动请求该链接。但 prefetch 的触发时机由浏览器内部策略决定，开发者无法强制。

适用场景/作用：

  • 理论上可用于预加载阶段触发 GET 请求，但实战价值极低
  • 不同浏览器（Chrome、Firefox、Safari）的 prefetch 策略差异大，行为不可预测
  • 仅作为了解，不推荐用于实战渗透

2、GET 诱导点击型

超链接诱导

原理：<a> 标签的点击属于 Top-level Navigation（顶层导航）。现代浏览器默认的 SameSite=Lax 策略对嵌套子请求（如 img、iframe）会阻止跨站 Cookie 携带，但对用户主动触发的顶层 GET 导航会放行 Cookie。这是 SameSite=Lax 的天然盲区。

适用场景/作用：

  • 目标 Cookie 已设置为 SameSite=Lax（此时 img/iframe 自动加载无法携带 Cookie）
  • 需要利用”用户主动点击”这一行为绕过 SameSite 限制
  • 配合钓鱼话术（如”点击领取福利”、”查看完整图片”）诱导用户点击
  • 短链接传播（微博、论坛、邮件）

关键风险：SameSite=Lax 对 top-level GET 请求不会拦截Cookie，这是 Lax 模式的天然盲区。

3、POST 表单提交型

POST 大部分都是是在一个页面中构造好一个表单，然后使用 JavaScript 自动提交这个表单。

原理：HTML <form> 的 method="POST" 配合默认的 enctype="application/x-www-form-urlencoded" 属于简单请求。浏览器直接发送，不触发 OPTIONS 预检，且自动携带目标域 Cookie（若 Cookie 的 SameSite 策略允许）。所有参数通过隐藏字段 <input type="hidden"> 静态硬编码，页面加载后通过 document.forms[0].submit() 自动提交。

适用场景/作用：

  • 目标接口接受标准表单数据（非 JSON API）
  • 目标 Cookie 未设置 SameSite=Strict，或显式设置为 SameSite=None
  • 同站攻击场景（子域劫持、共享 eTLD+1）
  • 目标未部署 CSRF Token，或未校验 Origin/Referer

① 标准自动提交表单

  • 编码为 application/x-www-form-urlencoded
  • 参数静态硬编码，无法动态读取目标站的 CSRF Token（受同源策略限制，B 站 JS 无法读取 A 站页面内容）

② 内嵌在 Iframe 内执行

原理：将表单和提交脚本封装在 srcdoc 属性的 iframe 中，使恶意代码与外层页面隔离。即使外层页面被审查，iframe 内的内容也不直接暴露，增加隐蔽性。

适用场景/作用：

  • 需要隐藏攻击代码，避免被前端安全扫描工具直接发现
  • 外层页面需要展示正常内容（如钓鱼页面），iframe 在后台静默执行
  • 绕过某些基于页面源码的简单过滤

③ 文件上传（Form 版）

原理：enctype="multipart/form-data" 表单提交的数据体使用 multipart 格式分隔（boundary），属于简单请求，不触发 CORS 预检。攻击者可以构造文件上传请求，覆盖用户头像、上传 WebShell、或利用导入功能执行批量操作。

适用场景

  • 目标存在文件上传接口（头像、证件照、附件）
  • 利用导入功能执行批量操作（CSV、Excel、配置文件导入）
  • 配合路径遍历覆盖敏感文件（如通过 save_path 参数控制保存位置）

4、POST 伪装 JSON 型（text/plain 绕过）

原理：HTML Form 无法直接设置 Content-Type: application/json（会触发非简单请求的 OPTIONS 预检）。但通过设置 enctype="text/plain"，浏览器将 Content-Type 设为 text/plain，这属于简单请求，直接发送而不预检。攻击者利用 name 和 value 的拼接特性，构造出近似 JSON 格式的数据体。若服务端 JSON 解析器容错性强（如忽略尾部多余字符），则可能成功解析。

适用场景/作用：

  • 前后端分离的 RESTful API，接口只接受 JSON 数据
  • 服务端未严格校验 Content-Type，或 JSON 解析器容错（如某些 Node.js 框架）
  • 目标部署了 CORS 但认为 “JSON 接口不会被 CSRF”（常见误区）

提交的数据体：

  • Content-Type 为 text/plain，属于简单请求，无预检
  • 若服务端 JSON 解析器容错（如忽略尾部 =test），则解析成功

二、脚本型 CSRF（Script-Based）

通过 JavaScript 主动编程构造请求，能力更强，但受 CORS 约束。

1、Fetch / XHR 简单请求型

原理：通过 fetch() 或 XMLHttpRequest 编程构造符合简单请求标准的请求（POST + application/x-www-form-urlencoded 或 multipart/form-data）。浏览器将其视为简单请求，直接发送而不触发 OPTIONS 预检。CORS 策略仅在响应返回后决定是否允许 JS 读取响应内容，但不会阻止请求发出和服务端执行动作。

适用场景/作用：

  • 需要动态生成攻击参数（如根据时间、用户行为调整 payload）
  • 需要探测响应状态（即使无法读取响应体，也能通过 then/catch 判断请求是否成功）
  • 在单页应用（SPA）中，利用已有的 JS 执行环境发起攻击
  • 配合钓鱼页面，在用户交互后触发（如”点击下载”后执行）

关键结论：CORS 阻止 JS 读取返回包，拦不住请求发送，后端仍会执行扣款。

2、Fetch / XHR 非简单请求型

原理：发送 application/json 或携带自定义 Header（如 X-CSRF-Token）的请求，这会触发浏览器的 OPTIONS 预检机制。浏览器先询问目标服务端”是否允许该跨域请求”，只有服务端在响应头中明确授权（Access-Control-Allow-Origin 包含攻击者域名且 Access-Control-Allow-Credentials: true），实际请求才会发出。

适用场景/作用：

  • 目标 CORS 配置错误（如允许 * 且允许 Credentials，或允许特定测试域名）
  • 内部测试环境、开发环境的 CORS 规则宽松
  • 配合子域劫持（同域下无 CORS 限制，JS 可直接发送任意请求）
  • 探测目标接口是否存在（通过预检响应或错误捕获）

3、文件上传（JS 版）

原理：使用 FormData 对象动态构造 multipart/form-data 请求体，通过 Blob 和 File 对象在内存中伪造文件内容，无需用户真实选择文件。fetch 发送时自动设置 Content-Type 为 multipart/form-data; boundary=...，属于简单请求。

适用场景/作用：

  • 需要精确控制文件内容（如构造 WebShell、恶意图片、篡改后的配置文件）
  • 需要同时控制文件名和路径参数（如通过 save_path 参数实现路径遍历）
  • 需要批量上传多个文件（通过循环 data.append()）

4、Beacon API（页面卸载强制发送）

原理：navigator.sendBeacon() 是浏览器提供的专门用于可靠发送数据的 API。它保证在页面卸载（关闭、刷新、跳转）前将请求发出，且该请求自动携带目标域 Cookie。请求为异步、非阻塞，且无响应回调——攻击者不需要读取响应，只需要确保动作执行。

适用场景/作用：

  • 需要确保请求”必定发出”，不受页面生命周期影响（如用户快速关闭页面）
  • 用于数据外带（如将窃取的信息发送到攻击者服务器）
  • 在用户离开钓鱼页面时触发最后的攻击请求（如”退出前转账”）
  • 无响应回调（攻击者不需要）
  • 不受页面生命周期影响

5、WebSocket CSRF

原理：WebSocket 连接的建立依赖于 HTTP Upgrade 握手请求。该握手请求由浏览器自动发起，自动携带 Cookie，且不受 CORS 策略约束（WebSocket 使用独立的 Origin 校验机制）。一旦握手成功，后续全双工通信在浏览器看来已”升级”，不再受同源策略限制。若服务端未严格校验 Origin 头或未实施 CSRF Token 机制，攻击者页面可直接建立连接并发送恶意帧。

适用场景/作用：

  • 实时通信应用（在线聊天、游戏、股票交易、协同编辑）
  • WebSocket 服务端未校验 Origin，或仅做简单字符串匹配（可被绕过）
  • 需要维持长连接进行多次操作（如持续发送指令）
  • 攻击内网 WebSocket 服务（配合 DNS Rebinding）

风险点：

  • 服务端可能不校验 Origin 头
  • 很多 WebSocket 服务端未部署 CSRF Token 机制

6、自动化链式攻击

原理：利用 JavaScript 的异步编程能力（Promise/await），将攻击拆分为多个步骤。第一步通过 fetch 获取 CSRF Token（如果 Token 端点未受保护或 CORS 配置允许），第二步将获取到的 Token 嵌入请求头或请求体，构造出服务端认可的”合法请求”。

适用场景/作用：

  • 目标部署了 CSRF Token，但 Token 可通过公开端点获取（如 /get-token 未做防护）
  • Token 未绑定用户会话（攻击者获取自己的 Token 后硬编码使用）
  • 配合 XSS 使用（XSS 下可直接读取页面 meta 标签中的 Token，实现完全自动化）

前提：Token 未绑定会话，或可通过 AJAX 读取。

三、组合型 CSRF

不依赖单一技术，通过组合多种手段突破现代防御。

1、HTTP 方法覆盖型

原理：Rails、Laravel、Express 等框架支持通过请求参数（如 _method）或 Header（如 X-HTTP-Method-Override）覆盖 HTTP 方法。开发者可能认为 DELETE/PUT/PATCH “不可能来自 HTML Form” 而仅对 POST 请求实施 CSRF 防护。攻击者通过方法覆盖，将 Form/JS 的 POST 请求伪装为 DELETE/PUT/PATCH，绕过防护逻辑。

适用场景/作用：

  • RESTful API 架构（大量使用 PUT/DELETE/PATCH）
  • 框架默认启用方法覆盖（如 Rails 的 config.action_dispatch.request_method）
  • 开发者仅对 POST 路由做了 Token 校验，忽略其他方法
  • 需要删除资源、全量更新数据、修改管理员权限

2、Clickjacking + CSRF

原理：即使目标部署了 CSRF Token，如果响应头未设置 X-Frame-Options 或 CSP 的 frame-ancestors，攻击者可通过 <iframe> 将目标页面嵌入到恶意页面中。通过 CSS 将 iframe 设为完全透明（opacity: 0.001），并在页面上方覆盖伪造的按钮（如”领取红包”），诱导用户点击。由于用户点击的是目标域页面中的真实按钮，页面中的 CSRF Token 会随表单自动提交。

适用场景/作用：

  • 目标存在 CSRF Token 但允许被 iframe 嵌套
  • 需要用户交互确认的敏感操作（转账确认、密码修改、OAuth 授权）
  • 目标未实施点击位置随机化或交互时间检测
  • 配合钓鱼话术，提高用户点击意愿

3、XSS + CSRF（终极绕过）

原理：XSS 使恶意脚本在目标域的浏览器上下文中执行。此时脚本发起的请求被视为同源请求，同源策略、CORS、SameSite 全部不再构成限制。脚本可以直接读取页面 DOM 中的 CSRF Token（如 meta 标签、隐藏表单字段），构造出完全合法的请求，或直接使用 fetch 调用目标域 API。

适用场景/作用：

  • 目标存在存储型或反射型 XSS 漏洞
  • 需要完全绕过 CSRF Token、CORS、SameSite 等所有前端防御
  • 需要读取响应内容（纯 CSRF 无法做到，XSS 可以做到）
  • 需要执行多步骤复杂操作（如先查询余额，再转走全部金额）

四、存储型与客户端 CSRF

1、富文本 / 评论区植入

原理：将 CSRF 的 payload（HTML 标签或 JavaScript）持久化存储在目标站点的数据库中（如论坛帖子、评论区、用户个性签名、博客文章）。当其他用户浏览包含该内容的页面时，浏览器解析并执行其中的标签/脚本，自动向目标域发起请求。

适用场景/作用：

  • 目标存在富文本编辑功能且过滤不严（论坛、博客、商品评价、留言板）
  • 用户资料展示区域允许 HTML/URL（如头像链接、个人简介）
  • 攻击具有”蠕虫”特性：一个用户植入，所有浏览者都触发
  • 可植入 HTML（触发无脚本型 CSRF）或 JS（触发脚本型/XSS）
  • 植入 HTML：<img src="https://A.com/logout"> → 触发 GET 型
  • 植入 Form：<form action="https://A.com/transfer" method="POST"> → 触发 POST 型
  • 植入 JS：fetch(...) → 属于 XSS，但可完美实现 CSRF

2、用户资料恶意链接

原理：利用社交平台、论坛、协作工具等允许用户设置外部链接的特性，将链接地址直接指向目标站点的敏感操作 URL。其他用户点击该链接时，触发 Top-level Navigation，携带 Cookie 执行操作。

适用场景/作用：

  • 社交网站个人主页的”个人网站”字段
  • 短链接服务（将恶意长链接缩短后传播）
  • 即时通讯工具中的卡片分享（如微信、飞书、Slack 的链接预览）
  • 利用社交关系链扩大攻击面（如”查看我的主页”诱导点击）

其他用户点击时触发 CSRF。

3、第三方组件注入

原理：现代网站大量使用第三方脚本（广告、统计、客服、A/B 测试、CDN 资源）。如果这些第三方组件的供应链被篡改（如 CDN 被劫持、广告网络被入侵、统计脚本被替换），恶意代码会在目标站点的上下文中执行，发起 CSRF 请求。由于第三方组件通常被目标站点信任，防御方可能忽略对其内容的校验。

适用场景/作用：

  • 使用公共 CDN 加载前端库（如 jQuery、Vue、React），CDN 被劫持
  • 接入第三方广告平台（AdSense、百度联盟），广告脚本被篡改
  • 使用第三方统计/客服工具（Google Analytics、百度统计、在线客服插件）
  • 供应链攻击（如 SolarWinds 事件模式，但针对 Web 前端）

4、PDF / Office 宏

原理：利用客户端软件（Adobe Reader、Microsoft Office）的脚本执行能力，在文档打开时自动发起 HTTP 请求。这些请求通过系统内置的浏览器组件或 HTTP 库发出，可能携带用户已登录的 Cookie（取决于系统环境和浏览器集成方式）。

适用场景/作用：

  • 钓鱼邮件附件（”发票.pdf”、”工资表.xls”）
  • 企业内部文档共享平台（如企业网盘、OA 附件）
  • 目标使用 Adobe Reader（支持 PDF JavaScript）或启用宏的 Office
  • 绕过企业邮件网关的链接过滤（恶意逻辑在附件内）

5、DNS Rebinding + CSRF

原理：攻击者控制域名 attacker.com 的 DNS 记录，并设置极短的 TTL（如 60 秒）。用户第一次访问时，DNS 解析到攻击者的公网服务器（获取恶意页面）。页面加载后等待 TTL 过期，再次请求 attacker.com 时，DNS 解析到目标内网 IP（如 192.168.1.1）。由于浏览器基于域名而非 IP 判断同源，此时浏览器认为请求是同域的，同源策略和 CORS 不再限制，Cookie 正常携带。

适用场景/作用：

  • 攻击仅允许内网访问的管理后台（路由器、OA 系统、数据库管理界面、CI/CD 面板）
  • 绕过基于 IP 白名单的访问控制（如 “仅允许 192.168.x.x 访问”）
  • 配合 CSRF 攻击内网中未做 Token 防护的敏感接口
  • 探测内网存活主机和开放端口

注：现代浏览器已引入 Private Network Access 预检，该手法在最新 Chrome/Edge 中效果有限，但在老旧浏览器、企业内网环境、IoT 设备管理后台中仍可能生效。

防护措施

CSRF 漏洞的本质是 服务器未对请求的真实性进行校验：服务器单纯依靠 Cookie 判定用户身份，默认携带 Cookie 的请求就是用户本人发起，没有额外校验请求来源、请求凭证，从而产生跨站请求伪造风险。我们需要检查目标站点是否缺失下面三类防护措施：

一、检查是否存在 CSRF Token

CSRF Token 是服务器生成的随机值，绑定用户会话，发起敏感请求时必须携带（可以放在表单字段csrf_token，或者放在 HTTP 请求头X-CSRF-Token）。 如果请求里没有 Token，或是 Token 固定不变、不会随着会话 / 请求更新，则防护失效，存在 CSRF 漏洞。

验证方法： 拦截两次相同敏感操作的请求（例如两次购买课程、两次修改邮箱），对比csrf_token的值：

  • 两次 Token 相同 → Token 没有动态生成，可被复用，防护失效；
  • 请求中不存在 Token → 缺少该层防护，继续下一步验证。

PS：Token 名字不一定带有 CSRF 字样，带不带只是参数命名习惯，不是判定标准。后端校验逻辑才是核心：只要这个令牌用来防御 CSRF，它就是 CSRF Token，名字可以随便取。

二、检查 Referer/Origin 验证是否严格

服务器可通过 Referer（请求来源页面地址）或 Origin（请求来源域名）判断请求是否合法。 如果校验逻辑宽松（例如只判断 Referer 字符串包含目标域名，可通过子域名方式绕过），则存在漏洞。

验证方法： 使用 Burp Suite 修改 Referer 头为http://evil.com或者http://target.evil.com（伪造子域名），重放请求：

  • 请求成功执行业务操作 → Referer/Origin 验证失效；
  • 删除 Referer 请求头之后，请求依旧可以成功执行 → 完全没有开启 Referer 校验。

三、检查 Cookie 的 SameSite 属性

SameSite 是 Cookie 的安全属性，用来限制跨站场景下浏览器是否自动携带 Cookie：

  • SameSite=Strict：完全禁止跨站请求携带 Cookie，可以防御 CSRF；
  • SameSite=Lax：仅允许部分跨站请求（GET 类型的页面跳转）携带 Cookie；
  • SameSite=None：允许跨站请求携带 Cookie（必须搭配 Secure 属性，否则属性不生效）。

验证方法： 查看目标会话 Cookie（例如 session）是否配置了 SameSite=Strict 或 SameSite=Lax：

  • SameSite 未设置，或是设置为 None 且没有 Secure 属性 → 跨站请求能够携带 Cookie，存在 CSRF 风险。

四、CSRF Token 和别的 Token

1、CSRF Token

  • 作用：跨站请求防护令牌，防跨站请求伪造
  • 绑定：当前用户会话 Session
  • 特点：
    1. 放在 当前页面表单 或者 请求头
    2. 同一会话下，每次刷新页面会更新（部分系统一次会话复用，属于弱防护）
    3. 不会存放在 Cookie 里（放 Cookie 就失去防护意义）
    4. 由前端页面获取，跟着 POST / 敏感请求一起提交

2、JWT / Bearer Token

  • 作用：身份认证令牌，放在 Authorization 头，身份认证，替代 Session Cookie
  • 特点：
    1. 放在 Authorization: Bearer xxx 请求头
    2. 本身是身份凭证；JWT 不能直接当做 CSRF Token
    3. 如果前端把 JWT 存在 localStorage，不会被浏览器自动带到跨站请求，天然不受 CSRF 威胁；
      如果把 JWT 存入 Cookie，每次请求浏览器自动携带 Cookie 中的 JWT 完成身份认证，此时依然存在 CSRF 漏洞。

3、验证码 token、短信 token、一次性业务 token

作用是校验手机号、图形验证码，用于业务校验，不是 CSRF 防护。

五、纵深防御

CSRF 是一个基础但持续进化的攻击面。它的危险性不在于技术有多复杂，而在于防御链条中的任何一环出现疏漏，都可能导致整个防护体系崩塌。从 SameSite 的盲区，到 Token 的实现缺陷，从 CORS 的配置错误，到框架的方法覆盖机制，每一个看似微小的疏忽都可能被攻击者利用。

对于防御者而言，CSRF 的防护必须是一套纵深防御体系：

  • 协议层：SameSite=Lax/Strict 作为第一道防线；
  • 应用层：CSRF Token 必须与会话严格绑定，且验证逻辑无例外；
  • 传输层：Origin 与 Referer 校验作为补充；
  • 交互层：敏感操作强制二次验证（短信、邮箱、密码确认）；
  • 展示层：X-Frame-Options 与 CSP 阻断 Clickjacking 组合；
  • 架构层：禁止不必要的方法覆盖，路由严格限定 HTTP 方法。

CSRF 不会因为框架的默认防护而自动消失。只要 Web 仍然依赖 Cookie 维持会话、只要浏览器仍然自动携带凭据、只要开发者仍然在防御实现上存在疏忽，CSRF 就会继续作为 Web 安全领域中一个基础、经典且不可忽视的威胁存在。

小结

基础部分至此为止吧，还有一些安全验证的研究以及漏洞的深度利用和各种绕过技术这些，甚至包括我上方写出来的一些利用技术，还得深入学习部分细节以及一些开发相关的web知识之后再来补充吧。

CSRF防护现状：

SameSite 不是终点，CSRF 确实是个经典漏洞，但 2021 年 Chrome 默认启用 SameSite=Lax 后，很多人认为它”死了”。事实并非如此：

SameSite Cookie 只是缓解手段 SameSite=Lax会拦截大部分跨站 POST 请求自动携带 Cookie，但对于顶级导航 GET 请求（超链接、地址栏跳转）依旧会携带 Cookie；如果业务将修改状态的敏感操作实现为 GET 接口，依旧可以被 CSRF 利用。而 SSO 单点登录、支付回调、广告追踪等业务场景，因业务需要必须配置SameSite=None; Secure，浏览器层面的防护直接失效，重新打开 CSRF 攻击面。

CSRF Token 也并非万能防护 Token 机制本身存在多种绕过条件：Clickjacking 点击劫持可以通过透明 iframe 嵌套目标页面，诱导用户真实点击，自动携带页面内合法 CSRF Token 完成请求提交；站点存在 XSS 漏洞时，攻击者可在同源环境直接窃取 CSRF Token；服务端代码逻辑缺陷，例如 “缺少 Token 参数时不做校验”、“仅对 POST 校验而忽略 GET 请求”，直接删除 Token 参数即可绕过防护。除此之外，Token 实现缺陷比完全缺失更加危险：Token 不绑定用户会话、只做存在性检查、框架本身存在算法缺陷，都会让 Token 防护形同虚设。

CORS 不能作为 CSRF 的防御防线 CORS 的作用是管控 JS 读取跨站响应，而非阻止请求发送。application/x‑www‑form‑urlencoded、text/plain、multipart/form‑data属于浏览器简单请求，不会触发 OPTIONS 预检，跨站请求可以正常抵达服务端并执行业务逻辑；如果目标站点 CORS 配置错误，攻击者 JS 甚至可以发送application/json请求并读取接口返回数据。

现代 API 架构存在防护认知误区 很多开发认为接收 JSON 的 RESTful 接口天然免疫 CSRF，事实并非如此。利用 HTML 表单enctype="text/plain"可以构造伪 JSON 请求体，绕过 Content‑Type 限制，欺骗容错性较强的后端 JSON 解析器实现 JSON‑CSRF。 同时开发者常会主观认为 DELETE、PUT 这类 REST 方法无法由浏览器 HTML 表单发起，从而省略防护；借助_method参数方法覆盖，或是 JS 脚本，就可以伪装成 PUT/DELETE 请求，打破这一防护假设。WebSocket 接口若缺失 Origin 握手校验，同样会产生 CSRF 风险。

内网、老旧系统是高危盲区 企业内部 OA 后台、老旧业务系统、API 网关、IoT 管理设备普遍缺少 CSRF Token、SameSite 等现代防护配置。结合 DNS Rebinding 技术，攻击者可以借助公网页面对内网服务发起跨站请求，完成内网穿透攻击。

XSS 属于 CSRF 防护的终极绕过方式：一旦站点存在 XSS 漏洞，攻击者处于同源上下文，能够读取 Token、构造任意请求，CSRF 整套前端防护体系会全部失效。

现代 CSRF 绕过技术

修改前端参数只是最基础的利用方式。实际攻击者面对 CSRF Token、Referer 验证、SameSite 等防御时，有多种高级绕过手段，之前文档里的 Clickjacking、XSS 联动、text/plain 伪装、方法覆盖、DNS Rebinding、自动化链式攻击、WebSocket、CORS 配置利用 等，本质上都是现代 CSRF 绕过技术的具体实现。CSRF 的防御从来不是”有没有 Token”的问题，而是每一层防御（SameSite、Token、Referer、CORS、框架内置保护）是否被正确实现且无例外。

一、绕过 SameSite Cookie

绕过手法 原理 对应之前章节
GET 型绕过 Lax SameSite=Lax 对 Top-level Navigation（超链接点击、地址栏输入）的 GET 请求仍会携带 Cookie 一、2.2 超链接诱导
SameSite=None 的 Cookie 跨域集成（SSO、支付回调、广告）必须显式设置 SameSite=None; Secure，直接重建攻击面 前置知识 / 全章节前提
子域名 Cookie 注入 控制 sub.target.com 设置同名 Cookie，覆盖或混淆主站 Cookie 二、6. WebSocket / DNS Rebinding 相关

二、绕过 CSRF Token

绕过手法 原理 对应之前章节
Clickjacking 携带 Token 透明 iframe 嵌套目标页面，诱导用户点击真实提交按钮，Token 随表单自动提交 三、2. Clickjacking + CSRF
XSS 窃取 Token 同源上下文直接读取 meta 标签或隐藏字段中的 Token，构造合法请求 三、3. XSS + CSRF
自动化链式攻击 先通过 AJAX 获取 Token 端点，再携带 Token 执行攻击（Token 未绑定会话或端点暴露） 二、6. 自动化链式攻击
Token 存在性检查缺失 服务端”有 Token 才验，没 Token 不验”，直接删除参数即可绕过 一、3. POST 表单（通用原理）
Token 验证方法不一致 仅 POST 验 Token，GET 不验 → 用 GET 或方法覆盖绕过 三、1. HTTP 方法覆盖
Token 可预测/硬编码 Token 基于时间戳、简单编码，或全局通用，攻击者可用自己账号获取后复用 二、6. 自动化链式攻击
框架级 Token 漏洞 如 Rails 曾将 OTP 密钥与密文明文拼接发送，攻击者可逆向解密生成合法 Token 二、6. 自动化链式攻击（原理提及）

三、绕过 Referer / Origin 校验

绕过手法 原理 对应之前章节
Referer 置空绕过 利用 `` 或 data: URI，使 Referer 为空，服务端”空则放行”策略被利用 原始文档提及
部分匹配绕过 服务端只检查 Referer 是否包含 target.com，攻击者注册 target.com.evil.com 即可绕过 原始文档提及
Origin 校验缺失 WebSocket 或某些接口不校验 Origin，或仅做简单字符串包含判断 二、5. WebSocket CSRF

四、绕过 CORS（针对脚本型攻击）

绕过手法 原理 对应之前章节
简单请求绕过预检 使用 application/x-www-form-urlencoded、text/plain、multipart/form-data，避免触发 OPTIONS，请求直达服务端 二、1. Fetch 简单请求型
CORS 配置错误 目标返回 Access-Control-Allow-Origin: * + Allow-Credentials: true，或显式允许攻击者域名 二、2. Fetch 非简单请求型
DNS Rebinding 使 attacker.com 先解析到公网，再解析到内网 IP，浏览器认为同源，CORS 不生效 四、5. DNS Rebinding

五、绕过 Content-Type / 协议层限制

绕过手法 原理 对应之前章节
text/plain 伪装 JSON HTML Form 无法发 application/json，但用 enctype="text/plain" 构造伪 JSON 数据体，绕过 CORS 预检并欺骗 JSON 解析器 一、4. POST 伪装 JSON
HTTP 方法覆盖 框架支持 _method=DELETE，开发者认为 DELETE “不可能来自 Form” 而不做防护 三、1. HTTP 方法覆盖
