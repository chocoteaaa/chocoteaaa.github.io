前置

链子特点：无命令执行，只能触发 DNS 请求（出网 DNSlog，用来检测是否存在反序列化漏洞，不能 RCE）

URLDNS 链的作用就是在目标主机中可能存在反序列化输入的数据的地方，传入序列化后的 URLDNS 利用链，如果目标主机解析了这个 URL 地址，那么证明该处存在反序列化数据的行为。然后就可以进一步尝试其他反序列化漏洞了。

主要用到的两个反射方法是反射获取类对象和反射修改私有成员变量。

此链不依赖于第三方的类，而是 JDK 中的内置的类和方法，所以不受 JDK 版本的限制。适用于目标没有回显的情况。这里用：JDK8u56 版本测试（几乎全版本 JDK 都能打，JDK8/11/17 都可以，JDK17 高版本会有模块限制）

URLDNS链根因

注意

细心的人之前可能就发现了！HashMap::put()里面的putVal方法怎么跟HashMap::readObject里面的putValue方法有点像啊？没错，是同一个方法 putVal()，方法本体完全没变，只是调用源头、传参标记、时机不一样。

put()里面的：putVal(hash(key), key, value, false, true);
readObject的: putVal(hash(key), key, value, false, false);

最后一个参数：evict：put：evict = true；readObject：evict = false

evict 意思是：是否在插入后执行 afterNodeInsertion（给 LinkedHashMap 用的回调），对 HashMap 本身没有影响，不会影响 hash (key)，不会影响 URL.hashCode，不会影响 DNS 触发。

那为何在HashMap::readObject里要再写一遍putVal来存入参数的方法呢？

答：序列化只是把「HashMap里面所有key、value对象的状态」打包成字节流；序列化本身不会保留 “这个map当初是怎么put进去的” 这个操作过程。反序列化只是重建对象，它要手动把key-value再塞回map里，所以它内部又调用一遍putVal。

这就是该链能被利用的原因，构造Poc时map.put调用到putVal即使存进去内容了，也是按照一个变量一个值的样子存起来的，序列化时也会被拿出来，反序列化再根据这些值重新调用putVal放进去。

解决问题

我们刚好遇到只要一put就立马解析的问题，刚好这里put完了hashCode也能被修改，所以流程：

1、先hashCode.set(url, 1);，设置字段值为 1
2、再map.put(url, "abc");，URL对象内部的hashCode私有字段值为 1，不解析
3、再hashCode.set(url, -1);，URL对象还在内存里活着，可直接改其内部hashCode 为-1
4、反序列化的时候根据这些值重新调用函数putVal触发 DNS解析。

序列化带走的是：URL对象{hashCode=-1, url="http://xxx"}，非初put之hash值1也。

网关一提

网关是离开本机所在网段后的“下一跳”地址。若目标 IP 不在本机网段内，数据包会先交给网关，再由它继续转发。
本机选路遵循两条规则：
1、最长前缀匹配：路由表中匹配度最高的那条优先；
2、metric 越小越优先（同前缀时）。

其他问题

1、hosts 文件优先级最高：写了映射就完全不发 DNS 查询。OOB 测试若图省事在 hosts 里加一条，平台永远收不到记录。
2、代理/加速器的 fake-ip 会接管 DNS：Clash TUN、迅游加速器等可能让查询在本地被就地应答，数据包根本没出去。
3、安全设备可能只拦 DNS：允许 TCP 443 出网、但丢弃陌生域名的 DNS 查询，这是企业/校园网常见策略。
4、IPv6 干扰：AAAA 查询失败也会拖慢解析；可用 -Djava.net.preferIPv4Stack=true 或 -Djava.net.preferIPv6Addresses=false。
5、URLDNS 的特殊性：它在 URLStreamHandler.hashCode() 里调 InetAddress.getByName()，只要“发起查询”就能被记录；而 JNDI/JRMP/HTTP 这类需要真实建立连接的链，必须先解析成功，否则直接中断。
