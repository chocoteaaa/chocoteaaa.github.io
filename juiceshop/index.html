离线解码Token原因

在浏览器直接登录可以自动带上Token，我们用 BP 的原因有以下4点

1. 确认身份等级：解码后看到 `role=admin`、`data.id=1`、`email=admin@juice-sh.op`，才能证明万能密码拿到的是管理员，而不是某个普通账号。
2. 看清 `claims` 结构，为后续实验做准备：实验 4 的 JWT 算法混淆需要知道要篡改的字段是 `data.email`，还要知道原算法是 `RS256`；这些信息必须先解码才能确定。
3. 报告取证：截图 `Header/Payload`，作为“登录绕过成功 + 管理员身份”的证据。

注意：前端把 Cookie 的过期时间设为 8 小时；后端签发的 token 也有有效期。过期后页面会 401，需要重新用万能密码登录拿新 token。

三组对比实验

在这个逻辑接口里，耗时要看 POST /profile/image/url 这一条的Timing的Waiting (TTFB)，在浏览器里面，提交URL后应该看的：Timing标签包含：

阶段 如果耗时大，说明
Queueing / Stalled 浏览器排队，与目标无关
Initial connection TCP 握手 / 代理连接
Waiting (TTFB) 服务端处理（包括容器内 fetch）
Content Download 响应体传输（这里只有 302，几乎为 0）

为什么这个接口看 TTFB ： profileImageUrlUpload.js 的逻辑是：

服务端是先 await fetch 再响应的，所以第一个字节返回之前，已经把目标 URL 拉取完了。因此：

对本接口来说，TTFB 确实能反映 fetch 的快慢

如果实现是真正的“立即 302、后台异步拉取”，TTFB 就不会包含 fetch
时间——那种情况下耗时根本不能作为判据。文档里说的“异步 302”与这个版本的代码不完全一致。

第一组：可达 URL：

  • 状态码：302
  • 响应体：Found. Redirecting to /profile
  • 耗时：约 10–30 ms（Waiting (TTFB)：20ms）
  • 可以看到图片已经被传上去了

第二组：不可达 URL：

  • 状态码：仍然是 302
  • 耗时：几毫秒（连接被立即拒绝）（Waiting (TTFB)：5ms）
  • 容器日志： warn: Error retrieving user profile image: fetch failed; using image link directly

第三组：云元数据地址

实测：

  • 本地 Docker 下快速失败（Waiting (TTFB)：2ms），仍返回 302；
  • 这是正常现象，不代表实验失败（文档也说明本地不可达）。

对比结论

目标 状态码 耗时 profileImage 结果（这个）
可达 302 10–30 ms /assets/public/images/uploads/1.jpg
不可达 302 < 10 ms 原始 URL
元数据 302 快速失败，同上 原始 URL

第一个要24ms左右，后两个都在10ms之内，区分度其实也不高，不能实现端口扫描或内网探测判断。

组 profileImage 值 含义

小结

理论上来说，只要能让服务端去访问 127.0.0.1:3000 的资源（apple_juice.jpg），就已经证明存在 SSRF，也就是第一个对照实验（http://127.0.0.1:3000/assets/public/images/products/apple_juice.jpg）

后面的对照组其实是测 oracle：看这个接口能不能通过 状态码 / 响应体 / 耗时 做端口扫描或内网探测判断。然后经测试发现响应看不出来什么东西。

准确来说应该是：

SSRF 已确认存在。由于接口对所有目标统一返回 302，不能把响应码/耗时当作端口探测 oracle；但它会把拉取到的响应体写入头像文件并允许攻击者读回（用我上面的方法），因此形成可回显的读型 SSRF。

在本靶场中，已验证可以读取 crapi-identity 的内部响应，并可借道访问无需认证的内部 GET 接口（如 crAPI 的订单/服务请求，泄露 VIN、邮箱、手机号）。云元数据地址在本地不可达，无法演示凭证窃取。
