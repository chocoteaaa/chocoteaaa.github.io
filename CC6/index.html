Java反序列化CC6链及史上最详细Payload提前触发根因及问题解决

发表于2026-11-06|更新于2026-11-06
|总字数:3209|阅读时长:15 分钟|浏览量:

前面分析了 Java反序列化的 CC1链和 LazyMap版的 CC1链以及 URLDNS链，现在开始分析 CC6链，其实分析完前面的内容后，看 CC6其实不难。

有什么问题直接看我的文章应该都可以解决😜😜，毕竟这么详细😜😜。

不过我看了一些文章，发现在解决 CC6的链子提前触发的问题上时，并没有详细解释根本原因，导致很多人根本看不懂，十分混乱，于是此文我便详细解释一下。

CC6 链其实就是 URLDNS链的前半加上 CC1链的后半，不过这句话导致很多人都误认为 CC6链和 URLDNS链提前触发的原因也是一样的，它们构造payload时put会触发hashCode，预触发逻辑确实相似，但本质不一样，如果不搞清楚后面解决问题也根本不知道为什么要那样去做：

URLDNS 是URL.hashCode计算时触发解析，靠固定字段hashCode=-1压制；CC6 预触发后会在LazyMap内部map留下可序列化的缓存，缓存随payload传到目标主机，使得目标端再次调用get时不会进入transform。

本来想分析 CC2的，先看一下不同链子的环境要求吧：

线路一览

链号 commons-collections 版本 JDK 限制 触发入口 执行方式
CC1 3.1 ~ 3.2.1 JDK < 8u71 AnnotationInvocationHandler.readObject TransformedMap / LazyMap + InvokerTransformer → Runtime.exec
CC2 4.0 无硬性限制 PriorityQueue.readObject → heapify TransformingComparator + InvokerTransformer → TemplatesImpl
CC3 3.1 ~ 3.2.1 JDK < 8u71 AnnotationInvocationHandler.readObject InstantiateTransformer + TrAXFilter → TemplatesImpl
CC4 4.0 无硬性限制 PriorityQueue.readObject → heapify InstantiateTransformer + TrAXFilter → TemplatesImpl
CC5 3.1 ~ 3.2.1 无 JDK 限制 BadAttributeValueExpException.readObject → TiedMapEntry.toString 复用 CC1 的 LazyMap + ChainedTransformer
CC6 3.1 ~ 3.2.1 无 JDK 限制 HashMap/HashSet 反序列化 → TiedMapEntry.hashCode 复用 CC1 的 LazyMap + ChainedTransformer
CC7 3.1 ~ 3.2.1 无 JDK 限制 Hashtable 反序列化 → reconstitutionPut → equals 复用 CC1 的 LazyMap + ChainedTransformer

一开始想先按命名顺序来，但 CC2、CC4 的 CC 版本要求为4.0，并且事实上 CC1~CC7 的编号不是按 “发现先后”、不是按 JDK 版本、不是按难易排序，只是 ysoserial 作者往项目里提交 Payload 源码时的顺序来编号的。

所以要循序渐进，可先吃透 3.x 版本，它们的Transformer体系、LazyMapのgadget是一套，上手连贯。看了很多文章主流顺序都是：CC1 → CC6 → CC3 → CC4 → CC2 → CC5 → CC7

  • 第一组（CC1）：基础发动机，AnnotationInvocationHandler
  • 第二组（CC6）：同发动机，换入口，绕过 8u71 补丁（HashSet）
  • 第三组（CC3）：CC1 入口，换执行体（TemplatesImpl）
  • 第四组（CC4、CC2）：collections4 独立分支（PriorityQueue + TemplatesImpl）
  • 第五组（CC5、CC7）：TiedMapEntry 剩余两个入口（toString /equals）

CC6

实际上 CC6 就是CC1的一个变种，它产生的原因是 CC1 被 JDK8u71 补丁干掉之后的：同发动机替换入口。并且没有 JDK 版本限制，后半段跟 CC1 一样，不同之处为通过TiedMapEntry.hashcode()去触发 CC1里的LazyMap.get()。

CC6 根因

我们的Poc这段代码：TiedMapEntry tiedMapEntry = new TiedMapEntry(lMap,"1");，实例化出的tiedMapEntry对象它传进去的就是LazyMap并且key值为1，然后又写一个map再.put传入tiedMapEntry对象（及无卵用的value:2），那么根据链子就是：

HashMap::put(tiedMapEntry, "2") –> HashMap::hash(tiedMapEntry) –> TiedMapEntry::hashCode(无参调用) -直达-> TiedMapEntry::getvalue(Map:lmap, Key:"1") -> LazyMap::get()

到LazyMap::get()这里面的时候，有一个很关键的判断：

查map存key否，否则get()补一个，并将map键值对的value补为factory.transform(key)

那么显然我们第一次传入的factory就是那个LazyMap，key值为1，没有这个，就会存入内部包装的map中。

👇👇👇👇👇👇👇👇

后续反序列化再调用LazyMap.get("1")，containsKey命中缓存，直接return，不进factory.transform；

👆👆👆👆👆👆👆👆

问：我们本地这里有缓存别人没有不一样可以用吗？也不行！
答：缓存就在这个被装饰的map里面，而这个map会跟着一起序列化进去，送到目标机器。

所以缓存不是只留在你的本地进程内存，它被序列化嵌入payload，跟着走到靶机那边。靶机拿到的时候，缓存已经存在了，链子直接卡死。

对比URLDNS

所以这其实和 URLDNS链的问题不一样，不过相似之处确实都是在.put方法里会直接调用hash方法执行整条链子触发payload，这里没有什么并修改了hashCode值的说法，并且这也不是导致反序列化的时候不会触发payload根本原因。

CC6 的问题关键在上述LazyMap::get方法里，而URLDNS问题关键在URL::hashCode里：

所以两个就是不一样的！
